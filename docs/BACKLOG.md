## Этап 1 — движок и данные

### Сделано в плане 1в (08.10.2026)

Проверка правил хука в CI и `*.enc.json` по содержимому (`check:data`, D-34), `data/` в сборке

  данные новее сайта дают понятную ошибку «обновите страницу».
- **Уникальность `id` корректировок** в файле — проверять при записи (админка, этап 2).

### Сделано в плане 1б (07.10.2026)

Скорость таймлайна (планы команд один раз на игру, баллы по дням — за один проход: 11 → 2 мс),
`computeGameStateFrom(prepared, today)`, порядок «ачивки операторов → бонусы → позиции», ничья
«первым вошёл» (D-28), ранг прошлых недель по составу той недели (D-29), `team_pace` по своему темпу.

- **Холодный первый расчёт.** На машине разработки (i5-12500H): две недели, 70 операторов с переводами
  и увольнениями, стартовые ачивки — ~6 мс; месяц — ~14 мс в прогретом режиме, первый прогон до ~55 мс
  (JIT). На i3 сотрудников в 3–4 раза дольше: месяц в прогретом режиме — у границы ARCH-2 (50 мс).
  Проверить на этапе 3 перф-тестом с замедлением CPU (QA-4); если нужно — общий лидерборд недель для
  состояния и для ачивок (сейчас считается дважды) и расчёт один раз на новые данные, а не на каждый
  опрос.

## Этап 2 — админка

- **«Долг» отрицательных шагов.** Команда на 5-й клетке, админ даёт −10 (показ 0), потом +3 — фигурка
  всё ещё на 0: шаги копятся ниже нуля. Так написано в FR-STEP-3; превью админки должно это показывать
  или обрезать сохраняемое значение.
- **Корректировка баллов** в форме админки — с полем «за какой день» (D-25).
- **Выдача и отзыв ачивки** в админке — с полем «за какой день / неделю» (`date`, D-29).
- **Состав из воронки — только активные.** В сентябрьской воронке заметная часть строк — люди без
  активности или с несколькими днями (уволенные, новички, не операторы). Если завести всех, план
  команд раздуется. Мастер первого состава предлагает тех, у кого есть показатели, остальных — списком
  «проверьте» (калибровка D-27).
- **Статистика ачивок** «сколько человек получили» (R-3 ТЗ) — для сверки порогов D-27 после первой игры.
- **Метки времени** админка пишет помощником `localTimestamp` (`src/data/time.ts`, D-11).
- **Запись данных** — `sealSeason` с `salt` и `reuse` (неизменные файлы остаются байт в байт, зрители
  не перекачивают их и не выводят ключ заново) + коммит через Git Data API (SEC-4).

## Этап 3 — сцена

- **Выбор подхода к локациям** (D-23): «расписная доска» (ИИ-арт автора из `refs/` как текстура
  плоскости + 3D-персонажи и немного объёмных объектов) против сборки из CC0-наборов моделей.
  Учесть бюджет текстур (≤ 64 МБ в GPU, §12.1): 4 картинки 2048² без сжатия — ~85 МБ с мипмапами,
  значит 1024² или сжатые текстуры (KTX2/Basis).
- **Число клеток на локацию** (OQ-18): прогнать демо-месяц этапа 1 при 10 и 20 клетках, показать автору.

Сцена этапа 0 — заглушка; при переходе на перспективную камеру с пролётами (D-23):

- `MapScene`: проп `angles` читается только при монтировании — R3F 9 не пересоздаёт камеру,
  заданную объектом настроек, а плитки при этом повернутся. Камеру этапа 3 держать в своём
  компоненте-риге (ref на камеру, пересчёт при смене `ui.camera` и размера окна). `zoom` сейчас
  тоже фиксируется по ширине окна при монтировании; `lookAtOrigin` дублирует поведение R3F.
- `FrameCounter` считает тики цикла R3F, а не реальные отрисовки WebGL: при своём 30-FPS тикере
  (PERF-1) дополнительно отдавать `gl.info.render.frame`.
- `App` размонтирует канвас на любом другом маршруте. Лидерборд (`#/leaderboard`) должен
  накрывать сцену и замораживать её (PERF-6), а не пересоздавать WebGL-контекст и ассеты.
- `npm run size` считает начальный JS по `modulepreload`-ссылкам; при `build.modulePreload: false`
  он бы недосчитал. Надёжнее — `build.manifest: true` и обход статических `imports` точки входа.
- **Численность в таблице команд (FR-LB-3):** `TeamState.headcount` — средняя за всю игру (с будущими
  новичками); для показа нужна текущая — число неуволенных в команде на сегодня.
