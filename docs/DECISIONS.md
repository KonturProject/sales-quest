Документ дополняет [`SPEC.md`](SPEC.md). **При расхождении действует этот документ.**
У каждого решения есть ID `D-*`; на него ссылаются в коммитах так же, как на `FR-*`.
Незакрытые вопросы и принятые по ним дефолты — в [`OPEN_QUESTIONS.md`](OPEN_QUESTIONS.md).

Согласовано с автором требований 27.09.2026.

`SPEC.md` — копия ТЗ автора с одной правкой: перед публикацией репозитория из строки версии
убраны имя автора и название компании (репозиторий публичный).

## Процесс

**D-1. Порядок этапов: 0 → 1 → 3 → 2 → 4 → 5** (в ТЗ §18 — 0 → 1 → 2 → 3 → 4 → 5).
Почему: самое рискованное — 3D на Intel HD — проверяется раньше; игру видно уже на третьей
итерации; импорт делается, когда появится пример рабочей таблицы (OQ-1). Критерии приёмки
этапов не меняются. Этап 3 работает на демо-данных `seed-demo`.

**D-2. Деплой на GitHub Pages — с этапа 0.** Репозиторий `KonturProject/sales-quest`
(публичный — бесплатный Pages только так), сайт https://konturproject.github.io/sales-quest/.
Почему: то, что проявляется только на живом GitHub — регистр имён файлов (Windows его
не различает, Pages различает), base-путь `/sales-quest/`, CI на Linux, кэш CDN Pages
(до ~10 мин — знаем по «Отделам против дракона»), Git Data API, права токена, реальная
задержка публикации, — ловится по одному, а не пачкой в конце. Критерий этапа 1
(«данные грузятся с Pages») без деплоя не проверить. Публичность истории поздний push
не отменяет (уходит вся история); защита — D-6 и правило «секретов в репозитории нет».

**D-3. Всё, что уходит наружу, — только после явного «да» автора требований:** коммит,
push, создание репозитория, включение Pages, деплой, скачивание сторонних ассетов.

**D-4. Проектные скиллы (§16.5) создаются, когда появляется их область**, а не все на этапе 0:
`engine-rules` — этап 1; `asset-pipeline`, `perf-budget-check` — этап 3; `import-profile` — этап 2;
`achievement-authoring` — этап 4; `season-rollover` — этап 5.
Почему: скилл, написанный до кода, описывает несуществующие пути и команды.

**D-5. Плагины, сторонние скиллы и MCP (§16.1–16.4) Claude сам не устанавливает.**
`/plugin install` — интерактивная команда терминального `claude`; сторонние скиллы — чужой код.
Похожие скиллы уже установлены (threejs-game, threejs-perf, game-qa, qa-game, add-3d-assets,
game-3d-assets). Что стоит поставить самому (typescript-lsp, context7) — в README.
Playwright подключается как npm-зависимость проекта. Платные генераторы (§16) не используются.

**D-6. Хуки (§16.7): git pre-commit-хук вместо хуков Claude Code.** Лежит в `.githooks/`,
подключается скриптом `npm prepare` (`git config core.hooksPath .githooks`), срабатывает
и на ручные коммиты. Блокирует коммит, если в добавляемых строках есть GitHub-токен
(`ghp_…`, `gho_…` и другие `gh?_…`, `github_pat_…`), если в `data/` добавлен JSON,
кроме `*.enc.json`, `version.json`, `seasons/index.json`, или если добавлена таблица
(xlsx/xls/xlsm/csv/ods) вне `tests/fixtures/` (SEC-10). Пути берутся из `git diff --name-only`,
а не из заголовков diff, — иначе переименования и бинарные файлы проходили мимо (ревью этапа 0).
Хук не видит коммиты через GitHub API и `--no-verify` — проверка тех же правил в CI запланирована
в `docs/BACKLOG.md`.
Автозапуск тестов после правок движка не делается — `npm run test:engine` входит в рабочий цикл.

**D-7. Производительность проверяется без доступа к рабочим ноутбукам.**
Playwright + Chromium с троттлингом CPU ×4 и программным WebGL (SwiftShader) — пессимистичная
оценка Intel HD. Скрытый счётчик `?stats=1` (FPS, draw calls, треугольники) — для любого,
кто когда-нибудь откроет игру на рабочем ПК и пришлёт скрин.
Целевое железо — из ТЗ (i3 4–5 поколения, HD 4400/5500, 6 ГБ). Известные реальные ноутбуки
команды (i3-6100U / i3-7020U, HD 520/620, 8 ГБ) чуть сильнее — ТЗ строже, держимся его.

**D-7a. Строгие бюджеты производительности — только для части, которую видят зрители** (27.09.2026).
Карта, HUD, лидерборд, карточки — всё, что открывают менеджеры и ТВ-табло, — держится
бюджетов §12 на слабом железе. Админка (импорт, корректировки, превью) работает только у
координатора на ПК с Intel Core i5 12-го поколения: для неё бюджеты §12 не действуют, разбор
тяжёлых выгрузок (16-МБ воронка) в браузере допустим. Граница обязательна: админка — отдельный
lazy-чанк (§12.1), код админки и SheetJS не попадают в начальный бандл и не загружаются
у зрителей; `npm run size` считает только начальный JS.

**D-8. Playwright в CI — с этапа 3** (вместе с перф-тестом QA-4). На этапах 0–2 e2e-тесты
запускаются локально; в CI — typecheck, lint, unit-тесты, сборка, проверка размера.

**D-8a. Unit-тесты в CI запускаются всегда, в том числе при пуше только `data/`** (отступление от DEP-2,
ревью этапа 0). С `concurrency: pages` GitHub отменяет ожидающий запуск, когда встаёт в очередь новый:
пуш кода B может быть отменён пушем данных C, и тогда C выкладывает код B без тестов. Экономия от
пропуска — меньше секунды. Заодно права `pages: write` / `id-token: write` выданы только джобе
деплоя, а checkout идёт без сохранённого токена (`persist-credentials: false`).

## Техника

**D-9. Роутинг — свой маленький хэш-роутер вместо react-router.** Маршрутов несколько
(`#/`, `#/leaderboard`, `#/admin`, на этапе 1 — `#/debug`), и роутер всё равно должен
разбирать `#/?k=<фраза>` (SEC-7). Зависимость ради этого не нужна.

**D-10. Бюджет начального JS (≤ 600 КБ gzip, PERF-BUDGET) проверяется `npm run size`**
в CI с этапа 0: сборка падает при превышении.

**D-11. Даты в движке и данных — календарные строки `YYYY-MM-DD` без часового пояса.**
«Сейчас» передаётся параметром `now`; движок берёт из него только календарную дату.
Почему: исключены сдвиги на день между UTC и московским временем. Метки времени (`at` корректировок
и журнала импорта) пишутся в местном времени с числовым поясом (`+03:00`); схема отвергает `Z`,
иначе действие в 00:30 по Москве попало бы на предыдущий день (ревью плана 1а).

**D-12. Шифрование (SEC-6): AES-GCM 256 + PBKDF2-SHA-256, 250 000 итераций** (ТЗ: ≥ 100 000).
Файлы одного коммита шифруются с общей солью, выведенный ключ кэшируется по соли —
слабый CPU выводит ключ один раз, а не на каждый файл. Модуль общий для браузера
и Node-скриптов (WebCrypto есть в Node 22).

**D-13. `metricsCounting: "inclusive"` (FR-SCORE-3) обрабатывается при импорте** (этап 2):
в `records` лежат уже игровые значения, движок про режим не знает.

## Механика: уточнения и разрешённые противоречия ТЗ

**D-14. Разбиение месяца на 4 недели (FR-TRACK-5)** — *снято D-24 (06.10.2026): игра больше не месяц,
недели игры — календарные недели внутри её периода.* Исходный текст для истории: Текст ТЗ («хвост присоединяется к 4-й»)
расходится с примером в приложении A, где короткое *начало* 01–04.10 присоединено к 1-й неделе.
Правило по умолчанию: период сезона режется на недели пн–вс; пока недель больше 4, крайняя
неделя с меньшим числом рабочих дней присоединяется к соседней (при равенстве — последняя
к предыдущей). Октябрь 2026: начало 01–04.10 — 2 рабочих дня, хвост 26–31.10 — 5 →
присоединяется начало, получается ровно пример из ТЗ. Правило только заполняет дефолт:
недели в конфиге сезона задаются вручную. См. OQ-4.

**D-15. «Стабильность» (`stable_top`)** — необязательный флаг `everyWeek: true` у правила `rank`
(топ-N в каждой неделе игры, D-24) вместо отдельного типа-композита, которого в схеме ТЗ нет.

**D-16. Тай-брейк лидерборда (FR-LB-5):** при равенстве баллов — метрики по убыванию веса,
затем ФИО по алфавиту. При дефолтных весах совпадает с ТЗ (`pay`, затем `inv20`), но без
жёстко прописанных id метрик (§0 п.4).

**D-17. `team_reset` (ADM-RESET-TEAM).** «Расчёт на момент сброса» задним числом не
восстановить — импорт перезаписывает дни. Поэтому корректировка хранит в `value` расчётную
позицию команды на момент сброса; итог = расчётная позиция − `value` + шаги `team_steps`,
сделанные после сброса. Результат детерминирован. Расчётная позиция берётся *до* ограничения
краем трека (`computedPosition` может быть больше конца зоны сверхплана): иначе команда, упёршаяся
в край, после сброса навсегда застывала бы на старте (ревью плана 1а). Ограничение 0…конец зоны
применяется только к итогу.

**D-18. Темп (FR-PACE-1):** `elapsedWorkingDays` — число *завершённых* рабочих дней
(строго раньше сегодняшней даты). См. OQ-10.

**D-26. Линия темпа — своя у каждой команды** (решение автора 06.10.2026, OQ-21). Ожидаемая позиция
команды = доля её плана, накопленная за завершённые рабочие дни, × длина трека. Норматив новичка
начинает копиться только с его первого дня в команде, поэтому новичок посреди игры не делает команду
«отстающей»; при неизменном составе линия совпадает с общей (N клеток в день). Явный план команды
(`teams[].targetPoints`) и режим `absolute` копятся равномерно — для них линия общая. Отход фигурки
назад в момент ввода новичка остаётся: план действительно вырос; админ увидит это в превью (FR-STEP-6).

## Срок игры (06.10.2026)

**D-24. Сезон — игра с произвольным сроком, по умолчанию две недели.** Заменяет «сезон = календарный
месяц» (§2, FR-SEASON-1/2, FR-TRACK-1/2/3/5, приложение A ТЗ). Требование автора: игра идёт две недели,
срок настраивается, и от срока пересчитывается число клеток трека.

- **Период** `period.start…period.end` задаёт админ; по умолчанию 14 дней (10 рабочих) с понедельника.
  Новый сезон «как прошлый» — того же срока, с понедельника после конца прошлого (этап 5).
- **Рабочие дни** — пн–пт периода минус `holidays`, либо явный список `workingDays`.
- **Длина трека считается от срока:** `track.cellsPerWorkingDay` = N клеток на рабочий день
  (по умолчанию **3** — решение автора 09.10.2026 по сцене плана 3а, OQ-18). Чтобы 4 локации были
  равными, число клеток округляется вверх до кратного 4: `cellsPerLocation = ceil(N × рабочих дней / 4)`,
  `trackLength = 4 × cellsPerLocation`. Две недели при N = 3 → 32 клетки, по 8 на локацию (при N = 2 —
  20 по 5).
  Праздник сам укорачивает трек.
- **Финиш = 100 % плана; отстающие до него не доходят — это нормально.** Зона сверхплана —
  `track.overflowPct` от длины трека, округление вверх; по умолчанию **50 %** (места до 150 % плана).
  Почему не 12,5 % из ТЗ: в игре лидеры заметно обгоняют план (оговорка автора), а при узкой зоне
  они упираются в её конец и стоят кучей, без различий между собой (OQ-20).
- **Всегда 4 локации, поровну:** локация k — клетки от `(k−1)·cellsPerLocation + 1` до `k·cellsPerLocation`;
  границы — 25 / 50 / 75 / 100 % плана. Локация больше не равна неделе (снимается FR-TRACK-2).
- **Недели игры** — календарные недели пн–вс, пересечённые с периодом; их столько, сколько выходит
  (для двух недель с понедельника — 2). Нужны недельным ачивкам и лидерборду за неделю.
  Правило D-14 (ровно 4 недели в месяце) снимается; рекомендуем начинать игру с понедельника (OQ-19).
- **`gateByWeek` (FR-TRACK-3) снимается:** локации не привязаны к неделям (закрывает OQ-5).
- **Цели по смыслу прежние:** дневные нормативы × рабочие дни в команде (R-2) — короче игра, меньше цель.
  Фолбэк для оператора без нормативов — `defaultDailyTargetPoints` баллов на рабочий день
  (вместо `targetPointsPerManager` за месяц).
- **Темп:** `pacePosition = floor(прошедшие рабочие дни / все рабочие дни × trackLength)` — около N клеток в день.
  *Уточнено D-26: линия темпа своя у каждой команды; эта формула — её частный случай при неизменном составе.*
- **Ачивки, завязанные на месяц** (пороги «за сезон», «до конца 3-й недели», «все 4 недели»),
  пересматриваются в плане 1б: пороги калибруются на двухнедельный срок, `early_bird` и `stable_top`
  считаются относительно недель игры.
- **Арифметика FR-STEP-4 сохраняется в тестах:** N = 2, 20 рабочих дней → 40 клеток; цель
  8 операторов × 7,5 балла × 20 дней = 1200; 990 баллов → 82,5 % → клетка 33.

**D-25. Корректировка баллов оператора относится к дню, за который она, а не ко дню ввода**
(ревью плана 1а). У `manager_points` есть необязательное поле `date`; без него — день ввода.
Такие корректировки считаются как записи показателей: только внутри периода игры (вне периода —
предупреждение, баллы не учитываются) и только по «сегодня» включительно; одинаково для баллов
команды и для лидерборда. Исправление за первую неделю, внесённое во второй, остаётся в первой.
Лидерборд тоже не считает записи с датой позже «сегодня» — как и позиции команд.

## Ачивки (07.10.2026)

**D-28. Ничьи в ачивках «кто первый»** (решение автора 07.10.2026). Данные — по дням, кто был первым
внутри дня, не видно.
- «Первая кровь» (`first`): из первого дня, в который у кого-то есть значение метрики, ачивку получает
  тот, у кого в этот день значение больше; поровну — все с наибольшим.
- «Первопроходец» (`team_position` с `firstOnly`): из команд, вошедших в локацию в первый такой день,
  получает та, что прошла дальше; на одной клетке — все такие команды.
- По тому же принципу (ревью плана 1б): в ачивках за место (`rank`, «Лидер недели», «Стабильность»)
  равные баллы делят место — при ничьей на границе топа ачивку получают все равные. Тай-брейк
  лидерборда D-16 по алфавиту для ачивок не применяется.

**D-29. Как считаются ачивки** (ACH-1…ACH-4, R-5; уточняет §6 ТЗ).
- **Ачивки — производное состояние**, как позиции: пересчитываются из данных при каждом расчёте и не
  хранятся. Учитываются данные по «сегодня» включительно. Дата получения — день данных, на которых
  условие выполнилось. Исправленные данные могут снять ачивку — так же, как сдвигают фигурку.
- **Окна:** «день» — день с данными; «неделя» — неделя игры (D-24); «игра» — весь период. Пороги за
  неделю и за игру — накопительные: ачивка в день, когда сумма дошла до порога. Серия (`streak`) —
  подряд идущие рабочие дни игры; выходные её не рвут и в неё не входят. Дни вне недель игры (выходные
  перед первым понедельником, OQ-19) идут только в окно «игра».
- **Доля** («Конвертер», `ratio`) может и падать, поэтому её судят по итогам завершённого окна: за игру —
  после игры, датой её последнего дня (ревью плана 1б; так и откалибровано в D-27).
- **Баллы в правилах** — по весам плюс корректировки баллов (D-25), **без бонусов за ачивки**: иначе
  ачивки зависели бы друг от друга по кругу. Бонус (`bonusPoints`, FR-SCORE-5) идёт в лидерборд
  оператора в день получения (выданная после игры — в последний день игры), в шаги команды — только при
  `achievementBonusAffectsSteps`. У командных ачивок бонуса нет. Порядок расчёта: ачивки операторов →
  бонусы → позиции команд → командные ачивки.
- **Ранг** («Лидер недели», «Стабильность») — по итогам завершённой недели (сегодня позже её последнего
  дня): лидерборд этой недели среди не уволенных на её конец, нужны баллы больше нуля. Дата — последний
  день недели. Так «Лидер недели» прошлых недель считается по составу той недели (R-5).
- **Рост** («Камбэк») — неделя игры к предыдущей; ачивка в день, когда сумма текущей недели дошла до
  базы прошлой недели плюс процент.
- **Личный план** («Досрочник») — дневной норматив оператора (или `defaultDailyTargetPoints`) × его
  рабочие дни в игре; выполнен — сумма баллов с начала игры дошла до плана не позже срока.
- **Командные ачивки** — по таймлайну: позиция и темп команды на конец каждого завершённого дня игры,
  выходные тоже (субботние оплаты двигают фигурку в субботу). Шаги админа учитываются со дня, когда
  внесены; после игры её последний день берёт и поздние корректировки — как текущее состояние, поэтому
  показанный финиш всегда даёт «Финишёра». «Впереди темпа N дней» считает только рабочие дни; у команды
  без плана темпа нет.
- **«Все в деле»** (`team_all_members`) — на любой день окна у каждого, кто в этот день в команде и не
  уволен, сумма метрики за дни в этой команде с начала окна не меньше порога. Новичок, пришедший позже,
  ачивку не отменяет; уволенный не мешает команде (уточняет R-5).
- **Уволенный** со дня увольнения новых ачивок не получает; полученные остаются (R-5).
- **Ручная выдача и отзыв** (ACH-2, ACH-3; уточнено ревью плана 1б). У выдачи и отзыва есть
  необязательный «день, за который» (`date`, как у D-25), без него — день ввода; по нему выбирается
  неделя («Звонок недели» за прошлую неделю можно выдать в понедельник). Выдача — ачивка этим днём;
  если правило выполнится само, дубля нет: остаётся более ранняя; вторая выдача за ту же неделю не
  учитывается, с предупреждением. Уволенному на этот день выдать нельзя (предупреждение). Отзыв снимает
  один «экземпляр» — ачивку целиком, а у еженедельной — только неделю своего дня: автоматическая больше
  не вернётся, выдачи до отзыва сняты, выдача после отзыва снова действует. Выключенная ачивка
  (`enabled: false`) не выдаётся ни сама, ни вручную.
- **ACH-4:** если по метрике игры у кого-то из состава есть только итоги-снимки (без данных по дням),
  правила, которым нужны дни (серия, порог за день, «первый»), отключаются с предупреждением.

**D-30. Схема правил ачивок — отличия от §6.1 ТЗ.** `threshold.value > 0` (порог 0 выдавался бы всем);
`team_all_members.period` — ещё и `season` (за игру); `target` — `before: 'week_end'` + номер недели
игры (вместо `week3_end`) или `before: 'date'`; `team_position.reach` — ещё и `overflow_end` (конец
зоны сверхплана), а `overflow` — шаг за финиш; `rank.everyWeek` — D-15; id метрики `points`
зарезервирован (баллы в правилах); `locationIndex` — только у `reach: 'location'`; `target.date` —
внутри периода; правила сверхплана при `overflowPct = 0` — ошибка. У `grant_achievement` и
`revoke_achievement` — необязательный `date` и ровно один субъект: оператор или команда. Движок:
`evaluateAchievements(prepared, today)` вместо `(config, records, adjustments, now)` — подготовленные
данные общие с позициями команд.

## Данные и доставка (08.10.2026)

Дизайн плана 1в — `docs/superpowers/specs/2026-10-08-stage-1c-data-delivery-design.md` (согласован с
автором 08.10.2026).

**D-31. Состояние клиента — свой маленький стор на `useSyncExternalStore`, без Zustand** (§13.2 ТЗ).
Стор один, подписчиков немного; зависимость ради этого не нужна (как D-9).

**D-32. Демо-игра** (DATA-16, решения автора 08.10.2026). Скрипт `seed-demo` делает двухнедельную игру
с понедельника текущей недели: 6 команд, около 50 вымышленных операторов, перевод, увольнение, новичок,
пара корректировок. Объёмы — только порядок величин (округлённые «на глаз», не цифры отдела). **Код
доступа к демо открытый** (в README): данные вымышленные. Рабочий код для настоящей игры — другой и в
репозиторий не попадает никогда.

**D-33. Файлы данных.** `version.json` (открытый) несёт отпечатки SHA-256 зашифрованных файлов игры;
клиент перекачивает только изменившиеся (`?v=<отпечаток>`), а сам `version.json` берёт без кэша (SYNC-1).
Конверт `*.enc.json` = `{v, alg, kdf, iter, salt, iv, ciphertext}` (SEC-6 + параметры вывода ключа, чтобы
их можно было сменить без миграции). Внутри файлов — `schemaVersion` (DATA-15); неизвестная версия —
понятная ошибка, миграции — с первым изменением схемы. Кэш на случай обрыва связи хранит файлы
зашифрованными и переписывается только при новых данных.
Уточнения ревью плана 1в:
- Соль — одна на игру, пока не сменился код: запись переиспользует неизменные файлы байт в байт
  (`sealSeason({salt, reuse})`), и зрители не перекачивают их и не выводят ключ заново; переиспользовать
  можно только файлы с той же солью и параметрами ключа. Итераций — не больше 5 000 000 (файл с огромным
  числом иначе «повесил» бы слабый ноутбук).
- Код, который не открывает ни одного файла, — «Код не подходит»; файл, который не открывается, когда
  остальные открылись, — повреждённые данные (плашка, опрос продолжается). Кэш, зашифрованный старым
  кодом, не решает за сайт: после смены кода (SEC-8) новый код сразу проверяется на сайте.
- Файл не той публикации (сайт ещё обновляется) запрашивается ещё раз мимо кэша браузера; не помогло —
  плашка «сайт обновляется», без замедления опроса. Запрос, который не ответил за 15 с, — «нет связи».
- Чтение данных в коде называется `DataSource` (`PagesSource`, `MemorySource`) — это читающая часть
  `StorageAdapter` из ARCH-1; запись (`commit`) появится на этапе 2.

**D-34. Проверка данных в CI по содержимому** (закрывает два пункта бэклога ревью этапа 0). `check:data`
проверяет каждый файл `data/`: `*.enc.json` обязан быть шифр-конвертом, открытые файлы — по своим схемам,
лишних путей нет, игра из `version.json` есть в списке, у файлов публикации одна соль; правила хука
(токены, таблицы) — по всем файлам репозитория. Срабатывает и на коммиты админки через GitHub API (этап 2),
и на `--no-verify`: не даёт такому коммиту попасть на сайт. Сам коммит в публичной истории git при этом
уже есть — поэтому главная защита остаётся на стороне того, кто пишет (хук, админка шифрует до записи).

**D-35. Состояние на дату — по тому, что было загружено к этой дате** (план 1в, уточнено ревью).
Запись видна, если к этой дате уже был импорт того же вида (профиль: воронка, оплаты), покрывающий её
день (`dateRange`): повторная загрузка месячной воронки перештамповывает старые дни новым импортом, но не
прячет их из прошлых дней. Корректировки, внесённые позже, не видны; отмена (`revoked`) действует со дня
отмены. «Данные от» — последний импорт к этой дате. Для живых данных ничего не меняется (всё в хранилище
уже загружено), а просмотр прошлого дня (`?date=`, повтор игры) и демо, где данные лежат заранее,
показывают день так, как он выглядел: данные за день появляются утром следующего, как в жизни. Значения
— сегодняшние (исправление задним числом видно и в прошлых днях), видимость — на ту дату.

**D-36. Код доступа в браузере и общий адрес GitHub Pages** (ревью плана 1в, к SEC-9). Сайты проектов
одного аккаунта GitHub живут на одном адресе `konturproject.github.io` и делят хранилище браузера: скрипт
любого другого сайта этого аккаунта (сейчас там «Отделы против дракона») технически может прочитать
сохранённый код. Пока это свои сайты — риск принимаем. Если на аккаунте появятся чужие или
непроверенные сайты — свой домен для игры (OQ-22).

## Сцена (08.10.2026)

Дизайн этапа 3 — `docs/superpowers/specs/2026-10-08-stage-3-scene-design.md` (согласован с автором
08.10.2026). Этап делится на планы 3а (сцена на заглушках и всё про производительность), 3б (вид: арты,

**D-37. Локации — «расписная доска», фигурки — фэнтези-герои** (решения автора 08.10.2026, к D-23).
Четыре панели доски — арты автора, которые перерисовываются по `docs/ART_BRIEF.md`: строго сверху, единый
стиль, тропа от середины левого края к середине правого, без нарисованных клеток и надписей. Текущие
картинки из `refs/` — референсы настроения: они в изометрии и разном ракурсе, на наклонённой камере
колонны и скалы выглядели бы «нарисованными на полу», а стыки — рваными. Генерирует автор. Клетки,
ворота и фигурки — объёмные поверх панелей. Герои — анимированный CC0-набор; скачивание — после «да»
автора (D-3). Картинки автора публикуются на сайте и в репозитории (разрешение автора).

**D-38. Рейтинг операторов на карте** (решение автора 08.10.2026, к §7). Панель поверх карты сменяется
каждые 15 секунд: по очереди каждая команда — её операторы по баллам и доля каждого в баллах команды
(«твой вклад в шаги фигурки»), — затем общий топ-10, и снова по кругу. Движок считает баллы оператора,
заработанные для каждой команды (R-1), чтобы доли складывались в баллы команды.

**D-39. e2e и перф-тест QA-4 в CI — отдельная задача, которая не держит деплой** (план 3а, к D-8).
Playwright с Chrome раннера и программным WebGL; отчёт QA-4 (`qa4.json`: кадры в секунду при CPU ×4,
вызовы отрисовки, треугольники, кадры в скрытой вкладке) — артефакт CI. Деплой ждёт только сборку и
unit-тесты: медленная CI-машина не должна задерживать публикацию данных админом (этап 2). Красный e2e
виден у коммита и разбирается отдельно. Очередь деплоя (`concurrency: pages`) — на задаче деплоя, а не на
всём workflow, иначе e2e одного пуша задерживал бы следующий; e2e ограничен 15 минутами, перф-тест идёт
отдельным проектом Playwright после остальных (ревью плана 3а). Проверки «покоя» ждут, пока все файлы сцены
скачаны и применены (`window.__sqLoading` = 0): на раннере CI герои разбираются секундами позже прихода, и
их кадр принимали за беспокойство сцены (10.10.2026). Скриншот-тесты QA-6 (`tests/e2e/visual.spec.ts`:
сцена в покое, весь трек, 2D-схема на демо с фиксированной датой; время проверки и текст слайда рейтинга
закрыты маской; допуск 1 % пикселей) сравнивают с эталонами этого ПК (win32); там, где эталона своей
платформы нет (Linux в CI), тесты пропускаются — шрифты и программный WebGL там рисуют иначе. Обычные e2e-тесты не проверяют частоту
кадров — только что кадры есть или их нет (покой, скрытая вкладка); частота — дело одного QA-4: на
раннере CI программный WebGL даёт ~11–12 к/с, и проверки скорости в обычных тестах там падали (10.10.2026).

**D-40. Правила рендера сцены** (план 3а, уточнены ревью; к PERF-1, PERF-7, PERF-8, FR-MOVE-1).
- Ходы всегда идут на полных 30 кадрах: «режим бездействия» (15 кадров, PERF-7) — только для «жизни»
  окружения (3б); ходы — главное событие, и экран чаще всего ждёт их без касаний.
- Тикер держит расписание 30 кадров в секунду и на мониторах 75 и 144 Гц, и после пропущенного кадра.
- Качество (PERF-8): частота кадров меряется только на ходах в обычном режиме; окно 2,5 с; два
  медленных окна подряд (< 80 % от 30 кадров, 5 с) — шаг вниз по DPR 1 → 0,85 → 0,75 → 0,6. Шаг
  запоминается на неделю, потом меряется заново.
- Над фигуркой — «+N шагов» / «−N шагов» (FR-MOVE-1); длинный проход сжимается в 3 с, поэтому дальше
  10 клеток прыжок короче 250 мс.
- Камера: углы `ui.camera` в конфиге — наклон 30–70° (пределы сцены), иначе первое касание дёргало бы
  камеру; сдвиг за край ленты двигает камеру целиком, а не поворачивает её; перетаскивание рисуется тем же
  тикером (≤ 30 кадров).

- **Позы — из плана хода, а не из часов:** прыжок клипом `Jump_Full_Short` на клетку (ход быстрее 250 мс
  на клетку — бег `Running_A`), после ворот или финиша — `Cheer`, и пауза перед следующей командой длится
  всю радость (`TIMING.cheerMs`, 1,7 с), чтобы камера её показала; в покое — первый кадр `Idle`
  лицом к зрителю. Поэтому в покое по-прежнему 0 кадров (PERF-1).
- **«Жизнь» локаций** — облако точек на панель (огоньки рун, снег, искры, золотые блёстки), движется в
  вершинном шейдере одной переменной времени; время идёт только на кадрах, которые и так рисуются (ходы,
  пролёты, перетаскивание), вне кадра облако отсекается (PERF-2).
- **Оптимизированные ассеты — в `src/assets/`**, а не в `public/assets/` (GFX-SRC-3): импорт с `?url` даёт
  хэшированные имена (DEP-4). Манифест `src/assets/manifest.json` пишет `npm run assets`, бюджеты и
  размеры проверяет `npm run check:assets` в CI (GFX-PIPE-3) — и что в `src/assets/` нет файлов вне
  манифеста. Лицензии — строго CC0-1.0, CC-BY-x.y или собственный арт автора (без -NC/-SA/-ND). Сейчас:
  панели 360 КБ (4 × 1024×559 WebP), герои 1,67 МБ, в GPU ~12,5 МБ текстур (бюджет 64).
- **Обзор** считается для любого угла камеры честной проекцией (перспектива, высота фигур); вид остаётся
  прямым (`ui.camera`). Лента из четырёх широких панелей в обзоре узкая — решение автора в D-42.


**D-42. Камера в покое — участок с командами, «змейка» в запасе** (решение автора 10.10.2026 по OQ-23, к D-23,
FR-MOVE-3). В покое камера показывает не всю ленту (она узкая — ~1/10 экрана), а клетки, где стоят команды:
- команды по позициям делятся на группы там, где соседей разделяет больше 4 клеток; кадр — клетки группы
  плюс по клетке с краёв, не меньше 6 клеток;
- одна группа — камера стоит (0 кадров); несколько — показывает группу лидеров, потом раз в минуту
  перелетает к следующей (≈1 с кадров в минуту) и по кругу; после любых ходов — снова лидеры;
- смена ждёт, пока идут ходы, вкладка скрыта или заморожена (PERF-3, PERF-4), и 2–3 минуты после касания
  камеры или кнопки зрителем (проверка раз в минуту); потом камера сама возвращается к группе, а если она
  и так там (щелчок без движения) — без пролёта и без кадров;
- пролёт к кадру покоя уступает ходам: пришли новые данные — первый пролёт хода начинается оттуда, где
  камера сейчас (ревью 3б-2); изменился размер окна во время пролёта — он заканчивается в новом кадре;
- «Весь трек» по-прежнему показывает всю ленту, «К лидеру» — фигурку лидера.
«Змейка» 2×2 (вторая строка зеркальна и идёт справа налево) сделана в `layout.ts` и включается одной
константой `BOARD_ARRANGEMENT` — в запасе, пока автор не выберет её (она расходится с «лентой» D-23).

**D-43. Доска лежит на столе** (просьба автора 10.10.2026 с референсом настольной игры на деревянном столе).
Под панелями — подложка в цвете их дымки (с площадками старта и финиша), вокруг — большой деревянный стол,
дальше — тёмная комната (фон; нарисованный пол ревью убрало: почти не отличался от фона, а стоил вызов и
закраску). Дерево рисуется кодом на холсте (без скачиваний) до арта автора (`docs/ART_BRIEF.md`, раздел
«Стол»). На столе — вещи KayKit (CC0): кружка, раскрытая книга, стрелы, колчан, стопка монет и свеча
сзади; щит и меч лежат спереди (перед доской — только плоское); дымовая бомба и монеты слева. Стол —
четыре вызова отрисовки, вещи — по одному на текстуру (5). Каждая поверхность оставляет дыру там, где на
ней лежит следующая, бока — стенки без крышек, материалы без освещения: в программном WebGL пиксель,
закрашенный дважды, стоил 8 к/с на QA-4 (22,5 → 30).

**D-44. Объём на панелях локаций** (просьба автора 10.10.2026: «чтобы карта не ощущалась плоской»; пакеты —
«да» автора 10.10.2026). Модели KayKit Medieval Hexagon и Dungeon Remastered (CC0, GitHub, закреплённые
коммиты, `npm run fetch-assets`) стоят на нарисованных деталях арта, а не на тропе (≥ 1 ед. от неё —
тест): в руинах — колонны на нарисованных капителях и обломки; во льдах — заснеженные пики по углам,
валуны на сугробах и заиндевевшие ели; на вулкане — тёмные скалы на чёрных островах и два факела у входа;
в небесах — деревья на островах и объёмные облака над морем облаков. Места выбраны по артам
(`src/scene/decor.ts`); подкраска (снег, базальт, иней, облако) сдвигает цвет модели, сохраняя свет и тень.
Вся сцена декора — один файл (`src/assets/decor/decor.glb`, ~200 КБ) и по одному вызову отрисовки на
текстуру (2) на все четыре локации; треугольников на локацию — до ~3 500 из 15 000 (§12.1, тест).


**D-45. Как проверяем скорость сцены и как бережём слабые машины** (решения автора 10.10.2026, к QA-4,
PERF-8, §12, D-39). Проверить на офисном ноутбуке (i3 + Intel HD) автор не может, поэтому:
- **приёмка QA-4 — на ПК автора с замедленным процессором:** `QA4_RATE=4` (по ТЗ, нужно ≥ 28 к/с), запас —
  `QA4_RATE=6` и `8` (команды — CLAUDE.md, «Проверка»). 10.10.2026: 30 к/с при ×4, ×6 и ×8; 46 вызовов,
  27 561 треугольник;
- **число QA-4 из CI — только динамика:** раннер рисует программно на 4 слабых виртуальных ядрах — 20 к/с на
  заглушках 3а, 14,1 на виде 3б, 10,9 со столом и объёмом (D-43, D-44). Красный QA-4 в CI деплой не держит
  (D-39), но рост цифр после правок — сигнал, падение — повод разобраться;
- **защита слабых машин — в плане 3в** («да» автора 10.10.2026): если ходы идут медленно, сцена по шагам
  упрощает себя, пока не станет плавной: разрешение (DPR 1 → 0,85 → 0,75 → 0,6, D-40) → без анизотропной
  фильтрации → без «жизни» локаций → без вещей на столе и объёма на панелях → предложение перейти на
  2D-схему (GFX-6). Шаги запоминаются на неделю, как DPR. Это расширяет лестницу PERF-8 (там: DPR →
  эмбиент → 2D) шагами для того, что добавили этапы 3б и 3б-2;
- реальный ноутбук остаётся открытым вопросом (OQ-24): если кто-то из отдела откроет сайт на нём, цифры
  можно снять со страницы `#/debug` (3в добавит туда частоту кадров);
- **сделано в 3в (10.10.2026):** ступени 0…7 (`src/scene/runtime/quality.ts`); шаг вниз пропускает ступень,
  которая на этом экране ничего не меняет (на экране с DPR 0,8 ступень 0,85 — та же картинка); DPR,
  сохранённый планом 3а, переходит на свою ступень; на `#/debug` — ступень, что она оставляет, последние 12
  окон ходов (к/с, среднее, худшее) и кнопка «Сбросить качество».

**D-46. HUD в стиле фэнтези-RPG** (просьба автора 10.10.2026: «панели с показателями выглядят ни к месту»;
референс — Divinity: Original Sin 2; макет поверх настоящей сцены утверждён автором 10.10.2026; к GFX-5,
GFX-4). Из референса берём только стиль — ни одной картинки игры, всё нарисовано в коде:
- **панели** — тёмные, с лёгкой фактурой, в двойной рамке (тёмный край и бронзовая линия) с ромбом и
  завитками в углах; заголовок панели — заглавными с орнаментальной линией («— ◆ РЕЙТИНГ ◆ —»); список
  рейтинга — на пергаменте; кнопки — тёмные плашки с бронзовым ободком и золотыми буквами;
- **карточка команды** — герб-щит цвета команды, полоса прогресса цвета команды («клетка 22 из 32 · 70 %»,
  заполнение — доля плана), темп зелёным или красным («в темпе» — золотым); счётчик слайдов рейтинга —
  ромбы (для экранного диктора — текстом «1 из 7»);
- **в том же стиле** — таблички имён над героями и «+N» (тёмная плашка и пергамент), экран кода доступа,
  загрузка, «нет страницы», сбой; будущие элементы 3в (мини-карта, 2D-схема, предложение схемы) — из того
  же набора стилей `src/hud/theme.css`;
- **шрифт — системный** Palatino Linotype (есть на любом Windows; запасные Book Antiqua, Palatino, Georgia):
  без скачиваний и лицензионных вопросов. Отдельный «резной» шрифт с кириллицей — в BACKLOG;
- **рамки и орнамент — векторные (SVG), нарисованы в коде** (`src/hud/frames/`), Vite встраивает их в CSS:
  чёткие на любом экране, без лишних запросов;
- **для слабых машин:** без `backdrop-filter`, размытых теней и свечения; HUD не перерисовывается по кадрам
  (меняется с данными и слайдами рейтинга раз в 15 с — проверено по слоям Chrome во время ходов). QA-4 после
  смены (10.10.2026): ×4 — 29,6–29,8 к/с, ×6 — 28,6–29,0, ×8 — 27,5–28,7 (до смены ~30 при всех трёх). Работы
  на кадр не прибавилось (процессорное время страницы и графики на кадр то же), но при ×8 кадр стоит на грани
  двух обновлений экрана, и сведение панелей поверх сцены иногда сдвигает его на третье: за 6 с то 162, то 180
  кадров при одних и тех же условиях. На ×4 по ТЗ и на ×6 запас есть; медленной машине первая ступень лестницы
  качества (DPR 0,85, план 3в) возвращает больше, чем стоит HUD.


**D-47. 2D-схема** (план 3в, 10.10.2026; к GFX-6, R-4, D-45). Та же игра под тем же HUD, без WebGL:
- **вид:** доска сверху — арты автора на панелях, клетки сцены в том же порядке (тот же `buildLayout`),
  ворота-ромбы, «СТАРТ», «ФИНИШ», команды — щиты цвета команды с табличкой «Алина С.» (полное имя — в
  карточках), флажки темпа, «+N шагов» на пергаменте. Панели лежат «змейкой» 2×2 (запас D-42): лента в
  одну строку на экран не помещается, змейка — целиком; клетки сверх плана в схеме сложены в три ряда
  рядом с финишем, а не тянутся зигзагом (иначе схема мельче на ~20 %);
- **ходы:** тот же план ходов сцены (`planMoves`) без пролётов камеры; план читается, пока идёт, 10 раз в
  секунду (чаще — если шаг короче, но не чаще 25), фишки переходят клетка за клеткой CSS-переходами; в покое
  не рисуется ничего. Как у сцены: те же позиции после пересчёта не обрывают ход, новый трек или сезон ходов
  не играет (схема пересоздаётся по id сезона), в скрытой вкладке часы ходов стоят (ревью 3в);
- **когда:** без WebGL 2 — сразу и без кнопки обратно; `?view=2d` / `?view=3d` — принудительно и
  запоминается (становится выбором, когда появляется в ссылке; своя кнопка зрителя потом его меняет); на нижней ступени лестницы качества HUD предлагает «Включить простую схему» («Карта идёт
  рывками на этом компьютере»); из схемы — кнопка «Объёмная карта». Выбор хранится в этом браузере;
- «Весь трек» — вся доска, «К лидеру» — приближение ×2,2 вокруг лидера; схема — отдельный ленивый чанк
  (~7 КБ), начальный JS не растёт.

**D-48. Мини-карта** (план 3в, 10.10.2026; к GFX-5, GFX-3, D-42). Плашка в середине верхней панели HUD:
весь трек одной полосой — четыре локации в цветах тем, клетки сверх плана штриховкой, ромб финиша, щиты
команд (на одной клетке — со сдвигом), риски темпа, бронзовая рамка — какую часть трека показывает камера.
Щит — кнопка: камера летит к команде, как «К лидеру», и смена групп в покое после этого ждёт (D-42).
Рамку сцена считает по нарисованным кадрам (края вида на земле → позиции клеток) не чаще 4 раз в секунду и
не во время ходов — только по их окончании: камера тогда следит за героем, а перерисовка HUD на каждом
обновлении стоила кадров ходов (QA-4 ×4 опускался до 27,9; без обновлений во время ходов — 29,6–30,1). В
2D-схеме рамки нет: схема видна целиком.

**D-49. ТВ-режим** (план 3в, 10.10.2026; к PERF-5, PERF-4, PERF-7, D-42, D-45). `?mode=tv` в ссылке офисного
экрана:
- сцена не замирает без фокуса и не замедляется без касаний (так и было в правилах рендера, теперь режим
  включается ссылкой); ходы и «жизнь» — 30 кадров;
- камера в покое — по командам по очереди, лидер первым, следующая через 20 с (команды на одной клетке —
  вместе), а не группами раз в минуту: у стены никто не крутит камеру сам;
- кнопок нет («Весь трек», «К лидеру», «Обновить», «Объёмная карта»): нажать некому, данные обновляются
  сами (SYNC); мини-карта остаётся — это табло; указатель мыши прячется через 3 с без движения;
- на нижней ступени лестницы качества схема включается сама: предложение «Включить простую схему» на стене
  нажать некому (D-45, D-47); ступень помнится неделю — ТВ раз в час смотрит, не кончилась ли она, и тогда
  возвращается к сцене и меряет её заново (ревью 3в).

**D-50. Остатки 3б: ворота, поворот героя, освобождение ресурсов** (план 3в, 10.10.2026; к FR-TRACK-1,
GFX-CHAR, PERF-12):
- **ворота** на чекпоинтах и финише — из уже скачанного пака KayKit Dungeon Remastered (CC0): две колонны с
  щитами (`pillar_decorated`) поперёк тропы и лежащая на них колонна (`column`) — «трилит» в стиле доски;
  финиш позолочен. Ворота отмечают трек, поэтому стоят на любой ступени лестницы качества (в отличие от
  декора); пока файл грузится или если не загрузился — простые ворота 3а. +6 тыс. треугольников (33,7 тыс.
  из 80), вызовов столько же;
- **поворот героя** после хода к зрителю — за 0,3 с плавно (кадры уже есть: после хода в плане пауза);
- **новый сезон — новая сцена** (`key` = id сезона): при размонтировании освобождаются геометрия, материалы,
  запечённые модели, герои и текстуры надписей (их кэш очищается вместе со сценой).

## Админка и запуск игры (10.10.2026)

**D-51. Этап 2 — сначала запуск настоящей игры** (ответы автора 10.10.2026: «запустить настоящую игру»,
«как можно скорее», подход «А: сначала запуск»; спецификация
`docs/superpowers/specs/2026-10-10-stage-2a-launch-design.md`, план 2а):
- **готовые профили двух выгрузок** вместо общего мастера разметки: воронка по дням и оплаченные счета
  размечены по сентябрьским файлам (`docs/IMPORT_FORMATS.md`), профили лежат в конфиге игры
  (`importProfiles`); мастер разметки — когда формат поменяется (2б). Блоки воронки ищутся по названиям:
  пропавший или переименованный блок останавливает импорт ошибкой; разбор сверяется с итогами групп и
  «Общим итогом» — расхождения показываются предупреждениями в превью;
- **импорт меняет только свои метрики** (D-20), файл полный за свой период (OQ-12): дни периода без
  чисел — нули; повтор того же файла не двигает фигурки — меняется только журнал импортов. Дни воронки —
  только с ненулевым «Общим итогом» отдела: выгрузка посреди месяца даёт будущие дни нулями, и они затёрли
  бы более свежий файл (ревью 2а, `docs/IMPORT_FORMATS.md` §1);
- **«кто это» без подсказок:** незнакомый человек с показателями в файле — решение админа (новый, это
  такой-то, игнорировать всегда), заранее ничего не выбрано; незнакомый без показателей не спрашивается;
  люди с показателями, которых админ снял в мастере, сразу попадают в «игнорировать» (ревью 2а);
- **записывается только то, что откроют зрители:** перед шифрованием каждый файл проходит их же проверку
  (`parseSeasonFile`); превью и запись — на одной и той же прочитанной версии, изменение, посчитанное на
  старой версии, — конфликт, а не тихий откат (ревью 2а);
- **демо — в `tests/fixtures/demo-data`**: dev-сервер и e2e берут его оттуда (`SQ_DATA_DIR`), сборка сайта —
  из `data/`. Запуск настоящей игры удаляет демо из `data/` тем же коммитом, что пишет игру;
- **фраза доступа настоящей игры** генерируется — четыре простых слова латиницей и две цифры (≈ 39 бит, с
  PBKDF2 SEC-6 подбор — месяцы работы видеокарты); можно свою — не короче 16 знаков и не демо-фраза (D-32).
  В репозиторий не попадает; ссылки с ней (`#/?k=…`, для экрана — `&mode=tv`) — только отделу;
- **подписи коммитов и название игры публичны** (репозиторий открытый): в них только даты и счётчики;
  админка отказывается записать подпись или название с именем оператора или руководителя;
- **состав из воронки:** группы → команды (`team1…`, `sourceCode` = код группы, D-21); люди с показателями в
  файле отмечены, без показателей — списком «проверьте»; норматив на каждого и по умолчанию для тех, кого
  добавит импорт (`defaultDailyNorms`); цель дня без нормативов = те же нормативы в баллах. Нормативы первой
  игры (выбор автора 11.10.2026): 3 качественных счёта, 1,5 разговора от 20 минут и 1 оплата в неделю
  (0,2 в день) — 9,5 балла; нормы отдела (5 / 2 / 2 в неделю) при нынешнем темпе оставили бы финиш
  недостижимым, а финиш должен быть достижим с усилием. Мастер подставляет их и показывает пересчёт на неделю;
- **табличка над героем** — «СР6 • Вера Соколова»: код группы перед именем руководителя (просьба автора
  11.10.2026); у команд без кода (демо) — только имя;
- **новая игра после настоящей** — только когда та кончилась: её файлы и фраза остаются, в индексе она
  `closed` (в зашифрованном конфиге статус прежний — читать его будет этап 5); поверх идущей игры — отказ;
- **ключ GitHub** — fine-grained, только репозиторий sales-quest, Contents: Read and write; хранится только в
  браузере координатора и уходит только на `api.github.com`; ключ без права записи не принимается;
- **каждое изменение — одна дорожка:** чтение с головы `main` → превью «было → станет» → один коммит только
  изменённых файлов (остальные — байт в байт, D-33) → плашка «Публикуется…», пока сайт не отдаст новую
  версию. Если `main` ушёл вперёд — «данные изменились», свежее превью, изменение не теряется.

**D-52. Состав и команды — пачкой правок** (план 2б-1, ответы автора 11.10.2026: «сначала состав и команды»,
«записывать пачкой»; спецификация `docs/superpowers/specs/2026-10-11-stage-2b1-roster-design.md`; к ADM-ROSTER-1…6,

- **превью** — люди каждой команды на день игры «было → станет», клетки команд и топ-10; **подпись коммита** —
  только счётчики: `состав: 1 новый, 1 перевод…; команды: 2 изменены, порядок`;
- **ответы GitHub словами:** 422 — конфликт только при «not a fast forward», иначе «GitHub отказал: …»; 403 с
  исчерпанным лимитом — «подождите», а не «нет прав»; 404 на репозиторий при входе — «у ключа нет доступа»;

**D-53. Корректировки по ходу игры — пачкой** (план 2б-2, ответы автора 11.10.2026: «бонус/штраф команде шагами»,

- **корректировка — значение, пачка — список** (`src/admin/corrections.ts`), как в D-52: своя пачка у экрана

- **показатели оператора за день** пишутся баллами: `manager_points` на `date` со значением «число × вес

  команде того дня (R-1) и в рейтинг оператора; счётчики показателей не меняются; будущая смена весов их не
  пересчитает. День — день игры и не позже сегодня; по умолчанию вчера. Уволенному можно (поздняя оплата).
  Минус, уводящий день оператора ниже нуля, — предупреждение, не отказ. Если поправленное потом придёт в
  выгрузке, оно посчитается дважды — форма предупреждает, корректировку нужно убрать (до 2б-3 — обратной);
- **на старт** — `team_reset` с расчётной клеткой команды сейчас (D-17, не меньше 0); дальше фигурка идёт от
  старта по новым данным. Отменить нельзя до 2б-3, поэтому — под «Редкое» и с галочкой;
- **номера** `adj-<ГГГГММДДЧЧмм>-<n>`, уникальны в файле (вторая пачка той же минуты продолжает счёт);

- **общие части экранов пачек:** черновик с превью и записью — `BatchDraft.tsx`, детали форм —

**D-57. Сцена моментов: подлёт, счётчик над фигуркой, салюты** (ответы автора 13.10.2026: «фигурка подлетает и

  салютов, счётчик сразу с итогом;
- **QA-4 с моментами** меряет именно ход (проба `window.__sqMoving`) и проверяет бюджеты §12.1.
- **салюты видны и на светлых локациях** (по скриншотам): искры обычной прозрачности со своим альфа-каналом и
  тёмной каймой, от уровня головы героя — аддитивные терялись на облаках и льду, а над головой их закрывали
  таблички; на схеме — кружки с каймой от щита; всплывашка шире под длинный текст, её фишка — поверх соседей.

- **значок у имени** — круглый «самоцвет» цвета редкости (синий — редкая, фиолетовый — эпическая, золото —
  легендарная), без буквы и иконки до этапа 4; круглый, чтобы не путать с ромбом команды. Только редкие и выше:
  обычные были бы почти у всех. Сначала легендарные, затем по порядку набора; до трёх, дальше «+N»; повторяемая —
  один значок. Везде, где в рейтинге имя: слайды команд, топ-10, «Герои дня»; не в тостах и не на карточках;
- **ачивки команды** — строкой под названием на её слайде, одинаковые названия сворачиваются («Первопроходец ×3»);
- **«Доска почёта»** — слайд после топ-10: ачивки операторов (редкие и выше), кто взял — по дате, имена короткие
  («Фамилия И.»), «×2», после трёх имён «и ещё N»; до 6 ачивок на слайд, дальше «1/2», «2/2»; уволенных нет,
  отпускники есть; легенда цветов внизу; без условий получения; нет слайда, пока ни у кого нет редкой ачивки;
- **новый значок ждёт баннер:** ачивки последней порции моментов скрыты, пока не доиграл её показ (часы показа
  читаются, не запускаются); потом значок один раз блестит, когда впервые на виду; «меньше движения» — без
  блеска. Упрощение: скрывает только последняя порция;
- **FR-LB-1 частично:** у имени — три самые редкие ачивки цветом редкости вместо «иконок трёх последних»;
  иконки, таблица лидеров и карточка менеджера (FR-LB-7) — этап 4.

**D-59. Финал игры** (ответы автора 18.10.2026: «салюты, лучшие из лучших, значимые достижения, лучшие МП среди
команд… на всех экранах, люди должны почувствовать вдохновение и причастность к общему делу», пьедестал «как на
любых соревнованиях»; спецификация `docs/superpowers/specs/2026-10-18-game-finale-design.md`, план
`docs/superpowers/plans/2026-10-18-game-finale.md`; к D-26, D-38, D-53, D-56, D-57, D-58, R-5):
- **старт — кнопка админа «Подвести итоги»** с последнего дня игры, после последней загрузки; по дате финал сам не
  включается (утром данные неполные). Записывается конфиг игры: `status: 'closed'` и `closedAt` — одним публичным
  коммитом «итоги игры ДД.ММ–ДД.ММ». «Вернуть игру» отменяет случайное нажатие. Список сезонов не меняется: его
  читает только мастер «Новая игра», который сам закрывает прошлую. Загрузки и корректировки после итогов
  разрешены — цифры финала живые;
- **церемония** (~минута, один раз на экран для каждого закрытия; часы — «часы прогона» D-56: ждут видимой вкладки):
  «Игра завершена» с салютом над всеми фигурками и общим итогом отдела → лучшие в командах → значимые достижения
  → лучшие из лучших (с третьего) → пьедестал (третье, второе, первое) и большой салют над победителем, камера к
  нему. Потом **итоговый экран** поверх карты до следующей игры; на ноутбуках — «Посмотреть церемонию ещё раз»,
  на ТВ кнопок нет. Рейтинг, карточки и моменты на это время скрыты; финал — только в живом просмотре (`?date=`,
  `?cells=` показывают карту). Браузер помнит сыгранное закрытие (`sq.finale.v1`);
- **пьедестал** — по клетке, на которой стоит фигурка (что видят все, с шагами админа), затем по проценту плана;
  место делят только при полном равенстве; подпись «клетка N · X % плана»; последних мест нет;
- **лучший в команде** — состав команды в последний день (как её слайд рейтинга), по баллам, принесённым этой
  команде; уволенных нет, отпускники есть; переведённый — герой только своей нынешней команды; команде без баллов
  карточка не нужна;
- **значимые достижения** — легендарные и эпические (операторов и команд), одинаковые названия сворачиваются
  («Первопроходец — СР1 ×2, …»), до 6 строк;
- **общий итог отдела** — показатели всех операторов (и уволенных) плюс ручные «показатели за день» (D-53): их
  число читается из написанной кодом причины «Оплаты +1: …» и сверяется с баллами; неразборчивое не угадывается;
- **салюты финала — не ход:** они не останавливают часы церемонии и моментов; пул D-57 (≤ 200 точек), кадры —
  только пока живут искры; «меньше движения» — без салютов, числа сразу;
- **уже открытые экраны** получают новую версию игры только после перезагрузки — после выкладки обновить
  офисный экран и вкладки сотрудников.

**D-60. Предпросмотр финала и две правки финала** (согласовано с автором 19.10.2026: «Посмотрю у себя в админке,
проверю пьедестал и лучших»; план `docs/superpowers/plans/2026-10-19-finale-preview.md`; к D-59, D-56):
- **«Посмотреть финал»** — кнопка на главной админки, пока игра идёт (после «Подвести итоги» её нет: финал уже на
  карте). Открывает поверх всей админки тот же итоговый экран, что увидят все, на данных на сейчас — как если бы
  итоги подвели в эту минуту (`previewFinale`: закрытие только в памяти); плашка «Предпросмотр финала — видите
  только вы, ничего не записано»; «Проиграть церемонию» — та же минута, по центру экрана. Карты в админке нет —
  салютов и камеры нет. Ничего не пишется: ни коммита, ни памяти браузера (`sq.finale.v1`) — после настоящих
  итогов церемония у автора сыграет как у всех;
- **карточка «лучший в команде»:** код группы («лучший в СР6»; без кода — «лучший в команде»), под ним
  руководитель отдельной строкой, ниже лучший оператор и баллы; длинные имена переносятся, а не обрезаются;
- **ничья на пьедестале:** у каждого места одна ступень, все команды этого места стоят на ней рядом (ничья за
  первое — победители вместе на широкой центральной ступени); пустое место сохраняет свою колонку, победитель
  остаётся в центре. Экранный диктор читает «1 место», «2 место», «3 место» по порядку (на экране — 2-1-3).

## Визуальное направление (28.09.2026)

**D-23. Как будет выглядеть сцена этапа 3** (уточняет GFX-1 и FR-MOVE-3). Автор показал референсы
(Monopoly Plus: объёмная доска-диорама, камера в движении, карточки игроков внизу экрана) и выбрал:

- **доска — линейная лента** слева направо, как в ТЗ (GFX-2 остаётся); референс ленты автор пришлёт (OQ-15);
- **камера — перспективная** вместо ортографической (GFX-1). Свободный зум и поворот в пределах.
  Во время хода — «пролёт»: камера подлетает к команде, ведёт фигурку по клеткам, задерживается
  на «+N шагов», переходит к следующей команде, потом возвращается к общему плану (расширяет FR-MOVE-3);
- **фигурки — 3D-персонажи-руководители**, как в ТЗ (GFX-CHAR);
- **стиль — «игрушечная диорама»** из low-poly CC0-наборов: мягкое запечённое освещение, пятна-тени.
  Живые тени от статики, bloom, размытие, отражения — только как уровень качества High, не у зрителей (PERF-9);
- **HUD — карточки команд внизу экрана**, как в референсе (DOM поверх сцены, GFX-5);
- **«жизнь» окружения** (машинки, флаги, вода) — во время ходов и в ТВ-режиме; в покое сцена замирает (OQ-16);
- порядок этапов не меняется: сначала движок (этап 1), вид — на этапе 3.

**Референс локации «Лава»** (28.09.2026): клетки — неровные каменные плиты с пунктирной рамкой,
цепочкой поперёк светящейся лавовой реки; путь идёт S-дугой от START к EXIT (вход и выход локации);
вокруг тёмные вулканические скалы с тлеющими трещинами, дым по краям, летящие искры.
Как делаем на слабом железе: плиты — low-poly камни (инстансинг), лава — плоскость с эмиссивной
текстурой (в покое — застывший кадр, во время хода — медленная анимация шейдером), свечение без
bloom — эмиссивные цвета, мягкие ореолы-спрайты по краям лавы и оранжевая подсветка камней снизу
(запечённая), дым — несколько крупных полупрозрачных спрайтов и туман сцены, искры — лёгкие частицы
только во время ходов.

**Референсы четырёх локаций** (28.09.2026) лежат локально в `refs/` (в git не попадают): древние руины,
ледяные скалы, вулкан (2 варианта), небеса, плюс 3 кадра Monopoly Plus. Локации — ИИ-арт автора;
автор разрешил использовать его в игре, если понадобится (кадры Monopoly Plus — только как ориентир).
Вариант для этапа 3 — «расписная доска»: картинка локации — текстура плоскости (один draw call),
сверху — 3D-персонажи, немного объёмных объектов и частицы; ближе к референсам и дешевле для
Intel HD, чем сборка из наборов моделей. Решаем на этапе 3 (`docs/BACKLOG.md`).

Почему это укладывается в бюджеты §12: пролёты идут только во время ходов, а данные обновляются
несколько раз в день; между ходами рендер по требованию — 0 кадров. Перспективная камера по нагрузке
не дороже ортографической. Уровень детализации Monopoly Plus (коммерческая игра с динамическим светом
и постэффектами) на Intel HD недостижим — целимся в тот же дух, а не в ту же картинку.

## Импорт реальных выгрузок (27.09.2026)

Автор принёс две реальные выгрузки; структура и разметка полей — в [`IMPORT_FORMATS.md`](IMPORT_FORMATS.md).

**D-19. Четвёртая форма данных импорта — «матрица»** (к трём формам DATA-3). Воронка — сводная
таблица: строки — группы и сотрудники, колонки — дни внутри именованных блоков показателей.
`ImportProfile` получает `mode: "matrix"` с описанием: лист, строки названий блоков / подблоков /
дат, колонка ФИО, колонки-флаги группы и сотрудника, и для каждой метрики — пара
«название блока + название подблока». Блоки ищутся по названиям, а не по буквам колонок.
Схема — на этапе 2 (импорт), вместе с остальными формами.

**D-20. Импорт заменяет только свои метрики: upsert по (оператор, дата, метрика)** (уточнение DATA-5).
Метрики приходят из двух файлов: воронка даёт `inv6` и `inv20`, выгрузка оплаченных счетов — `pay`.
Профиль импорта объявляет, какие метрики он поставляет, и загрузка не трогает остальные.
Файл считается полным за свой период (правило — IMPORT_FORMATS §4, OQ-12).

**D-21. У команды в конфиге сезона поле `sourceCode`** — код группы в выгрузках (`СР1`, `СР5`, …).
Нужно для подсказки команды нового оператора (DATA-11) и предупреждения, если оператор
в выгрузке числится не в той группе, что в составе. Появляется в схеме конфига на этапе 1.

**D-22. Метрики по разметке автора** (заменяет определения из §2 и приложения A ТЗ):

| id | Название в конфиге | Источник |
|---|---|---|
| `inv6` | Качественные счета | воронка: «Качественные счета, шт.» |
| `inv20` | Разговоры от 20 минут | воронка: «Разговоры от 20 минут, шт.» |
| `pay` | Оплаты | оплаченные счета: уникальные «№ счета», без «Академии», все статусы новизны, по «Дате оплаты» |

Id оставлены как в ТЗ — на них ссылаются формулы и ачивки. `inv6` — счета, `inv20` — разговоры:
разные сущности, вычитать нечего, поэтому `metricsCounting = "exclusive"` (закрывает OQ-2).
Веса по умолчанию прежние (1 / 3 / 10). По объёмам в выгрузках разговоров 20+ за неделю
заметно больше, чем оплат, так что при этих весах они могут давать больше баллов, чем оплаты;
калибровка — в первый месяц через ADM-WEIGHTS с превью (риски R-3, R-8 ТЗ).
Демо-данные `seed-demo` (этап 1) генерируются в порядке величин реальных выгрузок, чтобы пороги
ачивок проверялись на правдоподобных числах.

## Состав команд — дополнение к ADM-ROSTER (27.09.2026)

Требование автора: в филиале есть текучка, состав команд меняется через админку, без правки кода.
Модель данных и правила расчёта — этап 1 (движок, тесты); интерфейс — этап 2.

### Интерфейс

- **ADM-ROSTER-1.** Экран «Состав»: список команд, каждая раскрывается до операторов.
  У оператора — кнопки «Редактировать» и «Уволить». Внизу — «Добавить оператора».
- **ADM-ROSTER-2.** Форма оператора (добавление и редактирование): ФИО, команда, дневные
  нормативы по каждой метрике сезона (поля строятся из `metrics`: добавится метрика —
  появится поле; дробные значения допустимы, ≥ 0). При смене команды спрашивается дата
  перевода (по умолчанию сегодня). При смене ФИО старое ФИО автоматически уходит в алиасы,
  чтобы импорт продолжал узнавать человека.
- **ADM-ROSTER-3.** «Уволить» — подтверждение с датой (по умолчанию сегодня) и необязательной
  причиной. Уволенный сразу скрыт из лидерборда; его данные и ачивки сохраняются (итоги сезона,
  архив). В админке — список уволенных с кнопкой «Вернуть» (на случай ошибки).
- **ADM-ROSTER-4.** Кнопка «создать нового» на экране несопоставленных строк импорта (DATA-10)
  открывает ту же форму.
- **ADM-ROSTER-5.** Каждое изменение состава проходит общий путь админки (§8):
  превью → подтверждение → коммит → запись в журнал; отменяется через ADM-UNDO.
- **ADM-ROSTER-6.** В интерфейсе — «оператор», в коде и данных — `manager`.

### Модель данных

Заменяет поля `teamId`, `active`, `personalTarget` менеджера в §14:

```ts
managers: {
  id: string;
  fullName: string;
  aliases: string[];
  dailyNorms?: Record<MetricId, number>;                  // норматив в день по каждой метрике
  memberships: { teamId: string; from: string; to?: string }[]; // периоды в командах, даты включительно;
                                                                 // нет `to` — работает в команде сейчас
  firedAt?: string;                                        // дата увольнения; есть — скрыт из лидерборда
  firedReason?: string;
}[]
```

### Правила расчёта (решения автора от 27.09.2026)

- **R-1. Заработанное остаётся за командой.** Запись `(managerId, date)` идёт той команде,
  чей период покрывает `date`. Увольнение и перевод не отодвигают фигурку назад.
  Запись вне всех периодов (например, оплата пришла после увольнения) идёт команде
  ближайшего периода (OQ-11).
- **R-2. Цель команды** (FR-STEP-1, приоритет 2) = Σ по операторам, Σ по рабочим дням,
  проведённым в команде, `Σ_m dailyNorms[m] × weight[m]`. Пришёл 15-го — даёт норматив только
  за оставшиеся рабочие дни. Нормативов нет — `defaultDailyTargetPoints` за каждый рабочий день
  в команде (D-24; пример FR-STEP-4: 8 × 7,5 × 20 = 1200).
  Явный `teams[].targetPoints` по-прежнему в приоритете.
- **R-3. `activeHeadcount`** для режима `per_capita` — средняя численность:
  Σ рабочих дней операторов в команде / `totalWorkingDays`.
- **R-4. Смена весов меняет и цели** (нормативы × веса) — прогресс остаётся согласованным.
- **R-5. Уволенный** скрыт из лидерборда с момента увольнения; его баллы остаются в баллах
  команды, полученные ачивки — в истории. В ранжировании прошлых недель (`rank`) и в
  `team_all_members` участвуют те, кто был в команде в эту неделю; точное правило
  «был в команде в неделю» фиксируется тестами этапа 1.
