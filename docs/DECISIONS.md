## Процесс

**D-1. Порядок этапов: 0 → 1 → 3 → 2 → 4 → 5** (в ТЗ §18 — 0 → 1 → 2 → 3 → 4 → 5).
Почему: самое рискованное — 3D на Intel HD — проверяется раньше; игру видно уже на третьей
итерации; импорт делается, когда появится пример рабочей таблицы (OQ-1). Критерии приёмки
этапов не меняются. Этап 3 работает на демо-данных `seed-demo`.

**D-2. Деплой на GitHub Pages — с этапа 0.** Репозиторий `KonturProject/sales-quest`
(публичный — бесплатный Pages только так), сайт https://konturproject.github.io/sales-quest/.
Почему: то, что проявляется только на живом GitHub — регистр имён файлов (Windows его
не различает, Pages различает), base-путь `/sales-quest/`, CI на Linux, кэш CDN Pages
(до ~10 мин — знаем по «Отделам против дракона»), Git Data API, права токена, реальная
задержка публикации, — ловится по одному, а не пачкой в конце. Критерий этапа 1
(«данные грузятся с Pages») без деплоя не проверить. Публичность истории поздний push
не отменяет (уходит вся история); защита — D-6 и правило «секретов в репозитории нет».

**D-3. Всё, что уходит наружу, — только после явного «да» автора требований:** коммит,
push, создание репозитория, включение Pages, деплой, скачивание сторонних ассетов.

**D-4. Проектные скиллы (§16.5) создаются, когда появляется их область**, а не все на этапе 0:
`engine-rules` — этап 1; `asset-pipeline`, `perf-budget-check` — этап 3; `import-profile` — этап 2;
`achievement-authoring` — этап 4; `season-rollover` — этап 5.
Почему: скилл, написанный до кода, описывает несуществующие пути и команды.

**D-5. Плагины, сторонние скиллы и MCP (§16.1–16.4) Claude сам не устанавливает.**
`/plugin install` — интерактивная команда терминального `claude`; сторонние скиллы — чужой код.
Похожие скиллы уже установлены (threejs-game, threejs-perf, game-qa, qa-game, add-3d-assets,
game-3d-assets). Что стоит поставить самому (typescript-lsp, context7) — в README.
Playwright подключается как npm-зависимость проекта. Платные генераторы (§16) не используются.

**D-6. Хуки (§16.7): git pre-commit-хук вместо хуков Claude Code.** Лежит в `.githooks/`,
подключается скриптом `npm prepare` (`git config core.hooksPath .githooks`), срабатывает
и на ручные коммиты. Блокирует коммит, если в добавляемых строках есть GitHub-токен
(`ghp_…`, `gho_…` и другие `gh?_…`, `github_pat_…`), или если в `data/` добавлен JSON,
кроме `*.enc.json`, `version.json`, `seasons/index.json`.
Автозапуск тестов после правок движка не делается — `npm run test:engine` входит в рабочий цикл.

**D-7. Производительность проверяется без доступа к рабочим ноутбукам.**
Playwright + Chromium с троттлингом CPU ×4 и программным WebGL (SwiftShader) — пессимистичная
оценка Intel HD. Скрытый счётчик `?stats=1` (FPS, draw calls, треугольники) — для любого,
кто когда-нибудь откроет игру на рабочем ПК и пришлёт скрин.
Целевое железо — из ТЗ (i3 4–5 поколения, HD 4400/5500, 6 ГБ). Известные реальные ноутбуки
команды (i3-6100U / i3-7020U, HD 520/620, 8 ГБ) чуть сильнее — ТЗ строже, держимся его.

**D-7a. Строгие бюджеты производительности — только для части, которую видят зрители** (27.09.2026).
Карта, HUD, лидерборд, карточки — всё, что открывают менеджеры и ТВ-табло, — держится
бюджетов §12 на слабом железе. Админка (импорт, корректировки, превью) работает только у
координатора на ПК с Intel Core i5 12-го поколения: для неё бюджеты §12 не действуют, разбор
тяжёлых выгрузок (16-МБ воронка) в браузере допустим. Граница обязательна: админка — отдельный
lazy-чанк (§12.1), код админки и SheetJS не попадают в начальный бандл и не загружаются
у зрителей; `npm run size` считает только начальный JS.

**D-8. Playwright в CI — с этапа 3** (вместе с перф-тестом QA-4). На этапах 0–2 e2e-тесты
запускаются локально; в CI — typecheck, lint, unit-тесты, сборка, проверка размера.

## Техника

**D-9. Роутинг — свой маленький хэш-роутер вместо react-router.** Маршрутов несколько
(`#/`, `#/leaderboard`, `#/admin`, на этапе 1 — `#/debug`), и роутер всё равно должен
разбирать `#/?k=<фраза>` (SEC-7). Зависимость ради этого не нужна.

**D-10. Бюджет начального JS (≤ 600 КБ gzip, PERF-BUDGET) проверяется `npm run size`**
в CI с этапа 0: сборка падает при превышении.

**D-11. Даты в движке и данных — календарные строки `YYYY-MM-DD` без часового пояса.**
«Сейчас» передаётся параметром `now`; движок берёт из него только календарную дату.
Почему: исключены сдвиги на день между UTC и московским временем.

**D-12. Шифрование (SEC-6): AES-GCM 256 + PBKDF2-SHA-256, 250 000 итераций** (ТЗ: ≥ 100 000).
Файлы одного коммита шифруются с общей солью, выведенный ключ кэшируется по соли —
слабый CPU выводит ключ один раз, а не на каждый файл. Модуль общий для браузера
и Node-скриптов (WebCrypto есть в Node 22).

**D-13. `metricsCounting: "inclusive"` (FR-SCORE-3) обрабатывается при импорте** (этап 2):
в `records` лежат уже игровые значения, движок про режим не знает.

## Механика: уточнения и разрешённые противоречия ТЗ

**D-14. Разбиение месяца на 4 недели (FR-TRACK-5).** Текст ТЗ («хвост присоединяется к 4-й»)
расходится с примером в приложении A, где короткое *начало* 01–04.10 присоединено к 1-й неделе.
Правило по умолчанию: период сезона режется на недели пн–вс; пока недель больше 4, крайняя
неделя с меньшим числом рабочих дней присоединяется к соседней (при равенстве — последняя
к предыдущей). Октябрь 2026: начало 01–04.10 — 2 рабочих дня, хвост 26–31.10 — 5 →
присоединяется начало, получается ровно пример из ТЗ. Правило только заполняет дефолт:
недели в конфиге сезона задаются вручную. См. OQ-4.

**D-15. «Стабильность» (`stable_top`)** — необязательный флаг `everyWeek: true` у правила `rank`
(топ-N в каждой из 4 недель) вместо отдельного типа-композита, которого в схеме ТЗ нет.

**D-16. Тай-брейк лидерборда (FR-LB-5):** при равенстве баллов — метрики по убыванию веса,
затем ФИО по алфавиту. При дефолтных весах совпадает с ТЗ (`pay`, затем `inv20`), но без
жёстко прописанных id метрик (§0 п.4).

**D-17. `team_reset` (ADM-RESET-TEAM).** «Расчёт на момент сброса» задним числом не
восстановить — импорт перезаписывает дни. Поэтому корректировка хранит в `value` расчётную
позицию команды на момент сброса; итог = расчётная позиция − `value` + шаги `team_steps`,
сделанные после сброса. Результат детерминирован.

**D-18. Темп (FR-PACE-1):** `elapsedWorkingDays` — число *завершённых* рабочих дней
(строго раньше сегодняшней даты). См. OQ-10.

## Импорт реальных выгрузок (27.09.2026)

Автор принёс две реальные выгрузки; структура и разметка полей — в [`IMPORT_FORMATS.md`](IMPORT_FORMATS.md).

**D-19. Четвёртая форма данных импорта — «матрица»** (к трём формам DATA-3). Воронка — сводная
таблица: строки — группы и сотрудники, колонки — дни внутри именованных блоков показателей.
`ImportProfile` получает `mode: "matrix"` с описанием: лист, строки названий блоков / подблоков /
дат, колонка ФИО, колонки-флаги группы и сотрудника, и для каждой метрики — пара
«название блока + название подблока». Блоки ищутся по названиям, а не по буквам колонок.
Схема — на этапе 2 (импорт), вместе с остальными формами.

**D-20. Импорт заменяет только свои метрики: upsert по (оператор, дата, метрика)** (уточнение DATA-5).
Метрики приходят из двух файлов: воронка даёт `inv6` и `inv20`, выгрузка оплаченных счетов — `pay`.
Профиль импорта объявляет, какие метрики он поставляет, и загрузка не трогает остальные.
Файл считается полным за свой период (правило — IMPORT_FORMATS §3, OQ-12).

**D-21. У команды в конфиге сезона поле `sourceCode`** — код группы в выгрузках (`СР1`, `СР5`, …).
Нужно для подсказки команды нового оператора (DATA-11) и предупреждения, если оператор
в выгрузке числится не в той группе, что в составе. Появляется в схеме конфига на этапе 1.

**D-22. Метрики по разметке автора** (заменяет определения из §2 и приложения A ТЗ):

| id | Название в конфиге | Источник |
|---|---|---|
| `inv6` | Качественные счета | воронка: «Качественные счета, шт.» |
| `inv20` | Разговоры от 20 минут | воронка: «Разговоры от 20 минут, шт.» |
| `pay` | Оплаты | оплаченные счета: уникальные «№ счета», без «Академии», все статусы новизны, по «Дате оплаты» |

Id оставлены как в ТЗ — на них ссылаются формулы и ачивки. `inv6` — счета, `inv20` — разговоры:
разные сущности, вычитать нечего, поэтому `metricsCounting = "exclusive"` (закрывает OQ-2).
Веса по умолчанию прежние (1 / 3 / 10). По объёмам в выгрузках разговоров 20+ за неделю
заметно больше, чем оплат, так что при этих весах они могут давать больше баллов, чем оплаты;
калибровка — в первый месяц через ADM-WEIGHTS с превью (риски R-3, R-8 ТЗ).
Демо-данные `seed-demo` (этап 1) генерируются в порядке величин реальных выгрузок, чтобы пороги
ачивок проверялись на правдоподобных числах.

## Состав команд — дополнение к ADM-ROSTER (27.09.2026)

Требование автора: в филиале есть текучка, состав команд меняется через админку, без правки кода.
Модель данных и правила расчёта — этап 1 (движок, тесты); интерфейс — этап 2.

### Интерфейс

- **ADM-ROSTER-1.** Экран «Состав»: список команд, каждая раскрывается до операторов.
  У оператора — кнопки «Редактировать» и «Уволить». Внизу — «Добавить оператора».
- **ADM-ROSTER-2.** Форма оператора (добавление и редактирование): ФИО, команда, дневные
  нормативы по каждой метрике сезона (поля строятся из `metrics`: добавится метрика —
  появится поле; дробные значения допустимы, ≥ 0). При смене команды спрашивается дата
  перевода (по умолчанию сегодня). При смене ФИО старое ФИО автоматически уходит в алиасы,
  чтобы импорт продолжал узнавать человека.
- **ADM-ROSTER-3.** «Уволить» — подтверждение с датой (по умолчанию сегодня) и необязательной
  причиной. Уволенный сразу скрыт из лидерборда; его данные и ачивки сохраняются (итоги сезона,
  архив). В админке — список уволенных с кнопкой «Вернуть» (на случай ошибки).
- **ADM-ROSTER-4.** Кнопка «создать нового» на экране несопоставленных строк импорта (DATA-10)
  открывает ту же форму.
- **ADM-ROSTER-5.** Каждое изменение состава проходит общий путь админки (§8):
  превью → подтверждение → коммит → запись в журнал; отменяется через ADM-UNDO.
- **ADM-ROSTER-6.** В интерфейсе — «оператор», в коде и данных — `manager`.

### Модель данных

Заменяет поля `teamId`, `active`, `personalTarget` менеджера в §14:

```ts
managers: {
  id: string;
  fullName: string;
  aliases: string[];
  dailyNorms?: Record<MetricId, number>;                  // норматив в день по каждой метрике
  memberships: { teamId: string; from: string; to?: string }[]; // периоды в командах, даты включительно;
                                                                 // нет `to` — работает в команде сейчас
  firedAt?: string;                                        // дата увольнения; есть — скрыт из лидерборда
  firedReason?: string;
}[]
```

### Правила расчёта (решения автора от 27.09.2026)

- **R-1. Заработанное остаётся за командой.** Запись `(managerId, date)` идёт той команде,
  чей период покрывает `date`. Увольнение и перевод не отодвигают фигурку назад.
  Запись вне всех периодов (например, оплата пришла после увольнения) идёт команде
  ближайшего периода (OQ-11).
- **R-2. Цель команды** (FR-STEP-1, приоритет 2) = Σ по операторам, Σ по рабочим дням,
  проведённым в команде, `Σ_m dailyNorms[m] × weight[m]`. Пришёл 15-го — даёт норматив только
  за оставшиеся рабочие дни. Нормативов нет — `targetPointsPerManager / totalWorkingDays`
  за каждый рабочий день в команде (пример FR-STEP-4 при полном месяце не меняется: 8 × 150 = 1200).
  Явный `teams[].targetPoints` по-прежнему в приоритете.
- **R-3. `activeHeadcount`** для режима `per_capita` — средняя численность:
  Σ рабочих дней операторов в команде / `totalWorkingDays`.
- **R-4. Смена весов меняет и цели** (нормативы × веса) — прогресс остаётся согласованным.
- **R-5. Уволенный** скрыт из лидерборда с момента увольнения; его баллы остаются в баллах
  команды, полученные ачивки — в истории. В ранжировании прошлых недель (`rank`) и в
  `team_all_members` участвуют те, кто был в команде в эту неделю; точное правило
  «был в команде в неделю» фиксируется тестами этапа 1.
