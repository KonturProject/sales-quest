## 0. Как читать этот документ (инструкция для Claude Code)

1. Требования пронумерованы: `FR-*` — функциональные, `NFR-*` — нефункциональные, `DATA-*` — данные, `ADM-*` — админка, `ACH-*` — ачивки, `GFX-*` — графика, `PERF-*` — производительность, `DEP-*` — деплой. В коммитах и PR ссылайся на ID.
2. Слова **ОБЯЗАТЕЛЬНО / ЖЕЛАТЕЛЬНО / ОПЦИОНАЛЬНО** означают приоритет: MUST / SHOULD / MAY.
3. Всё, что помечено `[ОТКРЫТЫЙ ВОПРОС]`, не выдумывать — реализовать через конфиг с дефолтом из документа и вынести в `docs/OPEN_QUESTIONS.md`.
4. Любое игровое число (веса, длина трека, пороги ачивок) — **только из конфига сезона**, никаких констант в коде.
5. Работай по этапам из раздела 18. Не начинай этап N+1, пока не выполнены критерии приёмки этапа N.
6. Игровой движок (подсчёт баллов, шагов, ачивок) — **чистые детерминированные функции** без доступа к DOM/сети/времени (время передаётся параметром). Покрыть юнит-тестами до того, как делать графику.

## 1. Цель и контекст

**Цель:** визуализировать месячное выполнение плана отделом продаж как игру-«шагалку»: 6 команд (фигурка = руководитель группы) идут слева направо через 4 локации (= 4 недели месяца). Движение и лидерборд менеджеров считаются из реальных показателей, которые админ загружает из Excel-выгрузок.

**Бизнес-эффект:** прозрачность темпа плана, соревновательность между группами и между менеджерами, признание достижений через ачивки.

**Контекст эксплуатации:**
- Отдел: 6 руководителей групп, команды от 4 до 12 человек (итого ~40–70 менеджеров).
- Рабочие ПК: CPU уровня Intel Core i3 4–5 поколения, встроенная графика (Intel HD 4400/5500), ОЗУ до 6 ГБ, браузер Chromium-based (Chrome / Edge / Яндекс Браузер).
- Сеть: GitHub и Google работают стабильно; часть других сайтов в корпоративной сети может блокироваться.
- Источник данных: Excel-файлы (.xlsx), загружаемые админом вручную, многократно в течение дня/месяца.

## 2. Глоссарий

| Термин | Значение |
|---|---|
| Сезон | Один игровой цикл = один календарный месяц |
| Команда | Группа менеджеров под одним руководителем. На карте = одна фигурка |
| Фигурка | 3D-модель руководителя группы, стоит на клетке трека |
| Трек | Линейная последовательность клеток слева направо через 4 локации |
| Локация | Тематическая зона трека, соответствует неделе месяца (Л1…Л4) |
| Клетка | Шаг трека. Типы: обычная, чекпоинт (граница локации), финиш, зона сверхплана |
| Показатель (метрика) | `inv6` — счёт с разговором ≥6 мин; `inv20` — счёт с разговором ≥20 мин; `pay` — оплата |
| Вес | Множитель баллов за единицу показателя |
| Баллы | Σ(показатель × вес). Считаются для менеджера, баллы команды = сумма по менеджерам |
| Линия темпа | «Призрак»-маркер: где команда должна быть сегодня, если идёт ровно по плану |
| Импорт | Загрузка Excel-файла с показателями |
| Корректировка | Ручное действие админа (шаги, сброс, выдача ачивки), хранится в журнале |

## 3. Границы проекта

### 3.1 Входит в объём (IN SCOPE)
- Веб-приложение (SPA), открывается в браузере по ссылке, без установки.
- 3D-карта с изометрическим видом (~45° сверху), 4 локации, 6 фигурок, анимация перемещения.
- Расчёт баллов, шагов, ачивок по данным импорта и конфигу сезона.
- Лидерборд менеджеров и таблица команд.
- Система ачивок: автоматические по правилам + ручные.
- Админ-панель: импорт, корректировки, веса, ачивки, управление сезоном, журнал, откат.
- Импорт конфигурации сезона (команды, фигурки, локации, метрики, ачивки) из JSON/XLSX-шаблона.
- Цикличность: новый сезон «как прошлый» (сброс прогресса) или с изменениями.
- Бесплатный хостинг и бесплатное хранение общего состояния.

### 3.2 Не входит в объём (OUT OF SCOPE)
- Прямая интеграция с MS Dynamics CRM / API (только Excel-файлы).
- Личные кабинеты и логины для менеджеров (просмотр по общей ссылке).
- Мобильная версия как приоритет (должно не ломаться, но оптимизация — под ПК).
- Звук (ОПЦИОНАЛЬНО в этапе 5, по умолчанию выключен).
- Мультиплеерные действия игроков: игроки ничего не «ходят» сами, фигурки двигаются только от данных и админа.
- Денежные/премиальные расчёты — игра не является источником данных для премий.

## 5. Игровая механика

### 5.1 Баллы (FR-SCORE)
- FR-SCORE-1: баллы менеджера за период = `inv6 × w_inv6 + inv20 × w_inv20 + pay × w_pay`.
- FR-SCORE-2: дефолтные веса (редактируются в админке и конфиге): `w_pay = 10`, `w_inv20 = 3`, `w_inv6 = 1`. Порядок весов по ТЗ: оплаты > счета 20+ > счета 6+.
- FR-SCORE-3: `[ОТКРЫТЫЙ ВОПРОС]` Считается ли счёт с разговором ≥20 мин одновременно и счётом ≥6 мин в исходной таблице? Конфиг: `metricsCounting: "exclusive" | "inclusive"`.
  - `exclusive` (дефолт в игре): `inv6` — только счета с разговором 6–19:59, `inv20` — 20+. Двойного счёта нет.
  - `inclusive`: если в таблице `inv6` включает и 20+, импорт вычитает: `inv6_game = inv6_src − inv20_src`.
- FR-SCORE-4: баллы команды = сумма баллов активных менеджеров команды + ручные корректировки баллов (если есть).
- FR-SCORE-5: бонусные баллы за ачивки — ОПЦИОНАЛЬНО, поле `bonusPoints` у ачивки (дефолт 0). Бонус идёт в лидерборд менеджера, но **не** в шаги команды (чтобы ачивки не двигали фигурку «из воздуха»), если не включено `achievementBonusAffectsSteps: true`.

### 5.2 Справедливость между командами разного размера (ВАЖНО)
Команды отличаются по численности в 3 раза (4 vs 12 человек). Если шаги давать за абсолютные баллы, большая команда всегда побеждает. Поэтому режим расчёта шагов — параметр сезона `progressMode`:

| Режим | Формула прогресса команды | Когда использовать |
|---|---|---|
| `plan_percent` (**дефолт**) | `progress = teamPoints / teamTargetPoints` | Есть план в баллах на команду (или на менеджера) |
| `per_capita` | `progress = (teamPoints / activeHeadcount) / targetPointsPerManager` | План не задан, но хотим честное сравнение |
| `absolute` | `steps = floor(teamPoints / pointsPerStep)` | Команды одного размера или осознанное решение |

- FR-STEP-1: `teamTargetPoints` = явное значение из конфига команды **или** Σ персональных целей менеджеров **или** `activeHeadcount × targetPointsPerManager` (в этом порядке приоритета).
- FR-STEP-2: позиция на треке для `plan_percent` / `per_capita`: `position = min( floor(progress × trackLength), trackLength + overflowCells )`, где `trackLength = cellsPerLocation × 4` (дефолт `10 × 4 = 40`), `overflowCells` — зона сверхплана (дефолт 5 клеток: 100%→112.5%).
- FR-STEP-3: итоговая позиция = расчётная позиция + Σ ручных корректировок шагов − сбросы (см. 8, ADM-STEPS). Ограничение снизу 0, сверху `trackLength + overflowCells`.
- FR-STEP-4: **пример для тестов.** Команда 8 чел., `targetPointsPerManager = 150` → цель 1200. Факт: 60 оплат, 80 счетов 20+, 150 счетов 6+ → `600 + 240 + 150 = 990` баллов → прогресс 82.5% → `floor(0.825 × 40) = 33` клетка (4-я локация, 4-я клетка).
- FR-STEP-5: позиция **вычисляется** заново из всех данных при каждом изменении (детерминизм). Повторный импорт того же файла не должен сдвигать фигурку.
- FR-STEP-6: если пересчёт (например, после смены весов) уменьшает позицию, фигурка анимированно отходит назад; админ видит превью «было → станет» до применения (ADM-PREVIEW).

### 5.3 Трек, локации, клетки (FR-TRACK)
- FR-TRACK-1: трек линейный, слева направо, проходит через 4 локации по `cellsPerLocation` клеток. Последняя клетка каждой локации — **чекпоинт** (ворота/мост/переход в следующую локацию).
- FR-TRACK-2: при естественном темпе 25% плана в неделю команда оказывается в локации своей недели — локация «= неделя» получается автоматически, без жёсткой блокировки.
- FR-TRACK-3: ОПЦИОНАЛЬНЫЙ флаг `gateByWeek: true` — команда не может пройти чекпоинт локации N раньше начала недели N+1 (лишние шаги копятся и «выстреливают» в понедельник). Дефолт `false`.
- FR-TRACK-4: клетка финиша (позиция = `trackLength`) и зона сверхплана за ней (визуально — «за горизонтом», бонусная площадка).
- FR-TRACK-5: границы недель задаются в конфиге сезона (даты), по умолчанию: неделя 1 = с 1-го числа до первого воскресенья включительно и т. д.; если недель 5 (месяц начинается в конце недели) — хвост присоединяется к 4-й. `[ОТКРЫТЫЙ ВОПРОС]` подтвердить правило разбиения.
- FR-TRACK-6: ОПЦИОНАЛЬНО (этап 5): особые клетки-события (бонус +1 шаг, «привал» с подсказкой, клетка-ачивка). По умолчанию все клетки косметические.

### 5.4 Линия темпа (FR-PACE)
- FR-PACE-1: для каждой команды отображается полупрозрачный маркер ожидаемой позиции: `pacePosition = floor(elapsedWorkingDays / totalWorkingDays × trackLength)`.
- FR-PACE-2: рабочие дни берутся из конфига сезона (список дат), дефолт — пн–пт месяца без учёта праздников; праздники задаются списком.
- FR-PACE-3: в карточке команды — статус «впереди темпа на N клеток / отстаёт на N клеток».

### 5.5 Анимация движения (FR-MOVE)
- FR-MOVE-1: при получении нового состояния фигурка идёт по клеткам от старой позиции к новой (прыжок/шаг на каждую клетку, ~250–350 мс на клетку), над ней всплывает «+N шагов».
- FR-MOVE-2: если на одной клетке несколько фигурок — они расставляются по слотам (до 6 позиций вокруг центра клетки), без наложения.
- FR-MOVE-3: камера мягко следует к фигурке, которая двигается; после анимации возвращается в режим обзора.
- FR-MOVE-4: при первом открытии страницы фигурки ставятся сразу на текущие позиции без проигрывания истории; ОПЦИОНАЛЬНО кнопка «Реплей недели».

## 6. Ачивки

### 6.1 Модель (ACH-MODEL)
Ачивка = определение в конфиге сезона. Новые ачивки существующих типов добавляются **без кода** (через админку или импорт конфига). Новый **тип** правила требует кода (новый обработчик в `src/engine/achievements/rules/`).

```ts
type AchievementDef = {
  id: string;                 // "first_payment"
  title: string;              // "Открыл счёт"
  description: string;        // текст для карточки
  icon: string;               // id иконки из манифеста ассетов
  scope: "manager" | "team";
  rarity: "common" | "rare" | "epic" | "legendary";
  rule: AchievementRule;      // см. ниже
  repeatable: false | "weekly" | "daily"; // можно ли получить повторно
  bonusPoints?: number;       // дефолт 0
  enabled: boolean;
};

type AchievementRule =
  | { type: "threshold"; metric: MetricId | "points"; period: "day" | "week" | "season"; op: ">="; value: number }
  | { type: "streak"; metric: MetricId; minPerDay: number; days: number }            // N рабочих дней подряд
  | { type: "ratio"; numerator: MetricId; denominator: MetricId[]; minRatio: number; minDenominator: number; period: "week" | "season" }
  | { type: "rank"; by: "points"; period: "week" | "season"; top: number }              // место в лидерборде на конец периода
  | { type: "first"; metric: MetricId; within: "department" | "team"; period: "season" | "week" }
  | { type: "growth"; metric: MetricId | "points"; weekOverWeekPct: number; minBase: number }
  | { type: "target"; before: "week3_end" | "date"; date?: string }                       // личная цель выполнена до даты
  | { type: "team_position"; reach: "location" | "finish" | "overflow"; locationIndex?: number; firstOnly: boolean }
  | { type: "team_pace"; aheadDays: number }                                              // впереди темпа N дней подряд
  | { type: "team_all_members"; metric: MetricId; minEach: number; period: "week" }
  | { type: "manual" };                                                                   // только ручная выдача
```

- ACH-1: движок ачивок — чистая функция `evaluateAchievements(config, records, adjustments, now) → Unlock[]`. Каждая разблокировка содержит `achievementId`, `managerId|teamId`, `unlockedAt` (дата данных, на которых выполнено условие), `source: "auto" | "manual"`.
- ACH-2: ручная выдача «раньше времени» создаёт `Unlock` с `source: "manual"`; если позже правило выполнится автоматически — дубль не создаётся.
- ACH-3: ручной отзыв ачивки — корректировка `revoke_achievement` (с причиной).
- ACH-4: правила, требующие дневной детализации (`streak`, `threshold` за `day`, `first`), автоматически отключаются с предупреждением в админке, если импорт содержит только месячные итоги.
- ACH-5: при получении ачивки — тост/баннер на карте с иконкой и именем менеджера (очередь, не более 1 баннера за раз, 4 с).

## 7. Лидерборд (FR-LB)

- FR-LB-1: таблица менеджеров: место, ФИО, команда (цвет + имя руководителя), `inv6`, `inv20`, `pay`, баллы, число ачивок (иконки 3 последних), дельта места с прошлого обновления (▲▼).
- FR-LB-2: фильтры: период (сезон / неделя 1–4), команда. Сортировка по любой колонке, по умолчанию — баллы.
- FR-LB-3: таблица команд: позиция на треке, % плана, баллы, отставание/опережение темпа, численность.
- FR-LB-4: кнопка «Обновить» — принудительно перечитать данные с сервера (вне расписания опроса). Показ «данные от ДД.ММ ЧЧ:ММ» (время последнего импорта) и «проверено ЧЧ:ММ».
- FR-LB-5: при равенстве баллов — сортировка по `pay`, затем `inv20`, затем по алфавиту.
- FR-LB-6: лидерборд открывается как боковая панель поверх карты (карта при этом ставится на паузу рендера, см. PERF-6) и как отдельный маршрут `#/leaderboard`.
- FR-LB-7: карточка менеджера по клику: разбивка баллов по метрикам, график по дням (лёгкий SVG, без тяжёлых библиотек), ачивки.

## 8. Админ-панель

Маршрут `#/admin`. Видна только если в браузере сохранён GitHub-токен админа (раздел 13.5). Все изменяющие действия: **превью → подтверждение → запись одним коммитом → запись в журнал**.

|---|---|---|

## 9. Импорт данных

### 9.1 Источник
- DATA-1: Excel-файлы `.xlsx` (также принимать `.xls` и `.csv`) — копии рабочих таблиц. Формат таблиц будет предоставлен позже → `[ОТКРЫТЫЙ ВОПРОС]`. Поэтому импорт строится на **профилях сопоставления колонок**, а не на жёстком формате.
- DATA-2: файл парсится **в браузере админа** (SheetJS). Исходный файл никуда не загружается и не коммитится — в хранилище попадают только агрегированные записи по менеджерам/датам.

### 9.2 Профиль импорта (Import Profile)
```ts
type ImportProfile = {
  id: string;                       // "dynamics_daily_v1"
  title: string;
  sheet: string | number;           // имя или индекс листа
  headerRow: number;                // строка заголовков (1-based)
  mode: "daily" | "mtd_snapshot";   // построчно по дням или накопительный итог «на дату»
  columns: {
    manager: string;                // заголовок колонки с ФИО
    date?: string;                  // обязательна для mode=daily
    inv6?: string; inv20?: string; pay?: string;
    // ИЛИ режим «сырые события»: одна строка = один счёт/оплата
    eventType?: string;             // колонка типа события
    callDurationSec?: string;       // длительность разговора → классификация 6+/20+
  };
  eventMapping?: { invoiceValues: string[]; paymentValues: string[] }; // значения eventType
  snapshotDate?: "from_cell" | "from_filename" | "ask";                  // для mtd_snapshot
  dateFormat?: string;              // "DD.MM.YYYY" и т.п.
  metricsCounting: "exclusive" | "inclusive"; // см. FR-SCORE-3
};
```
- DATA-3: поддержать три формы данных (что окажется в реальных таблицах — неизвестно):
  1. **daily** — строка = менеджер × дата с числами `inv6`, `inv20`, `pay`;
  2. **mtd_snapshot** — строка = менеджер с накопленными итогами на дату; дата снимка берётся из ячейки/имени файла/спрашивается у админа;
  3. **events** — строка = один счёт/оплата с длительностью разговора; агрегация в daily на лету (≥360 с → `inv6`-диапазон, ≥1200 с → `inv20`).
- DATA-4: мастер импорта при первом файле нового вида: выбор листа → строки заголовков → сопоставление колонок выпадающими списками → превью первых 20 строк → сохранить как профиль. Дальше профиль определяется автоматически по набору заголовков.

### 9.3 Идемпотентность и повторные загрузки
- DATA-5: `daily` и `events`: upsert по ключу `(managerId, date)` — новые значения **заменяют** старые за эту дату. Повторный импорт того же файла не меняет состояние.
- DATA-6: `mtd_snapshot`: хранить снимки `(managerId, snapshotDate) → totals`. Итоги сезона = последний снимок. Дневные значения для ачивок = разница соседних снимков (если снимок один — дневные ачивки недоступны, ACH-4).
- DATA-7: импорт может покрывать любой диапазон дат; строки вне дат сезона — отбрасываются с предупреждением.
- DATA-8: каждый импорт = запись `ImportLog` (файл, хэш содержимого SHA-256, профиль, диапазон дат, кол-во строк, кто, когда). Если хэш уже импортирован — предупреждение «файл уже загружался», но разрешить.

### 9.4 Сопоставление менеджеров
- DATA-9: нормализация ФИО: trim, схлопывание пробелов, `ё→е`, регистр; сравнение по «Фамилия Имя» и по алиасам из состава.
- DATA-10: несопоставленные строки → экран разрешения: «привязать к существующему», «создать нового менеджера в команде X», «игнорировать всегда». Решение сохраняется как алиас.
- DATA-11: если в таблице есть колонка руководителя/группы — ОПЦИОНАЛЬНО использовать её для автоподсказки команды нового менеджера.

### 9.5 Импорт конфигурации сезона (лёгкий импорт для цикличности)
- DATA-12: единый шаблон `season_template.xlsx` (скачивается из админки) с листами:

| Лист | Колонки |
|---|---|
| `Season` | id, title, startDate, endDate, progressMode, cellsPerLocation, overflowCells, targetPointsPerManager, gateByWeek, holidays (через запятую) |
| `Teams` | teamId, leaderName, characterId (из каталога моделей), color (#hex), targetPoints (опц.), order |
| `Managers` | managerId, fullName, teamId, aliases (через `;`), personalTarget (опц.), active |
| `Locations` | index (1–4), title, themePackId, weekStart, weekEnd |
| `Metrics` | metricId, title, weight |
| `Achievements` | колонки `AchievementDef`, правило — JSON в колонке `rule` |

- DATA-13: тот же конфиг принимается как `season.json`. XLSX конвертируется в JSON и валидируется одной zod-схемой. Ошибки — построчно с именем листа и ячейкой.
- DATA-14: частичный импорт: можно загрузить только лист `Managers` или только `Achievements` — остальное не трогается.

## 10. Цикличность и сезоны (FR-SEASON)

- FR-SEASON-1: жизненный цикл: `draft → active → closed`. Активный сезон один.
- FR-SEASON-2: «Новый сезон без изменений» = клон конфига активного сезона с новыми датами (следующий месяц), пустые данные, пустые разблокировки ачивок. Одна кнопка.
- FR-SEASON-3: «Новый сезон с изменениями» = клон + редактирование в админке или импорт `season_template.xlsx`/`season.json` (замена фигурок, локаций, метрик, весов, ачивок, состава).
- FR-SEASON-4: закрытый сезон архивируется в `data/archive/<seasonId>/` (конфиг + данные + итоги) и доступен для просмотра «Зал славы» (только чтение).
- FR-SEASON-5: ОПЦИОНАЛЬНО: сквозные ачивки/статистика между сезонами («3 месяца подряд в топ-3»).
- FR-SEASON-6: метрики — расширяемый список. Добавление новой метрики (например, `meetings`) = строка в листе `Metrics` + колонка в профиле импорта; код не меняется.

## 11. Графика и ассеты

### 11.1 Вид и камера (GFX-VIEW)
- GFX-1: 3D-сцена, **ортографическая камера** под ~45° сверху (pitch 45°, yaw 45° по умолчанию — классическая «изометрия», настраивается в конфиге).
- GFX-2: карта — горизонтальная лента 4 локаций слева направо; трек из клеток-плиток змейкой/дугами внутри локации, общая линия движения слева направо.
- GFX-3: управление: перетаскивание — панорамирование по оси трека, колесо — зум в ограниченных пределах, клик по фигурке — карточка команды, клик по локации — наезд камеры. Кнопки «Весь трек» / «К лидеру».
- GFX-4: над каждой фигуркой — табличка с именем руководителя и цветом команды (плоский спрайт/текст в 3D, не DOM-элементы на каждый кадр), кольцо цвета команды под ногами.
- GFX-5: HUD поверх сцены (DOM): мини-карта трека с 6 маркерами и линиями темпа, дата данных, кнопки лидерборда/обновления, текущая неделя.
- GFX-6: фолбэк: если WebGL недоступен или FPS < 15 после автоснижения качества — режим **2D-схемы** (SVG-трек с иконками фигурок), вся функциональность сохраняется.

### 11.2 Локации (GFX-LOC)
Каждая локация = «тематический пак» (`themePackId`), собираемый из готовых CC0-наборов. Дефолтная четвёрка:

| Неделя | Тема | Источник ассетов (CC0) | «Жизнь» в активном состоянии |
|---|---|---|---|
| 1 | Деревня / старт | Kenney Nature Kit, KayKit Medieval Hexagon | качание деревьев (вершинный шейдер), вращение мельницы, дым из трубы (спрайты) |
| 2 | Город | Kenney City Kit (Commercial/Suburban), Kenney Car Kit | машинки по кольцу, мигающие окна |
| 3 | Горы / замок | Kenney Castle Kit, KayKit Dungeon/Medieval | флаги, факелы (эмиссия + мерцание), облака |
| 4 | Порт / финиш | Kenney Pirate Kit, Kenney Watercraft Pack | волны (дешёвый шейдер воды), корабль качается, салют на финише |

- GFX-LOC-1: тематический пак описывается JSON-манифестом: список моделей, их расстановка (или ссылка на сцену `.glb`, собранную в Blender), список анимированных объектов и тип анимации.
- GFX-LOC-2: замена локации на другую = новый пак + ссылка в конфиге сезона. Без изменений кода.
- GFX-LOC-3: при необходимости сборки сцены в редакторе — ОПЦИОНАЛЬНО использовать Blender (бесплатно) и экспортировать одну `.glb` на локацию.

### 11.3 Фигурки (GFX-CHAR)
- GFX-CHAR-1: 6 фигурок-руководителей из каталога `characters/*.glb`. Каталог ≥ 10 вариантов на выбор, чтобы можно было менять между сезонами.
- GFX-CHAR-2: анимации: `Idle`, `Walk`/`Jump` (перемещение по клетке), `Cheer` (ачивка/финиш). Отсутствующая анимация → фолбэк на процедурный подпрыг.
- GFX-CHAR-3: цвет команды применяется тинтом (материал-оверрайд) или цветной деталью (флаг/шапка), не отдельной моделью.
- GFX-CHAR-4: ОПЦИОНАЛЬНО: фото руководителя на щите/табличке (загружается админом, сжимается до 128×128 WebP).

### 11.4 Источники ассетов (только бесплатные, приоритет — крупные библиотеки)

| Библиотека | Лицензия | Что берём | Формат |
|---|---|---|---|
| **Kenney.nl** (kenney.nl/assets) | CC0 | Nature, City, Castle, Pirate, Car, Holiday, Mini Characters (анимированные), UI-паки, Game Icons | GLB/GLTF/FBX/OBJ, PNG |
| **KayKit / Kay Lousberg** (kaylousberg.itch.io, github.com/KayKit-Game-Assets) | CC0 | Adventurers (персонажи + 75 анимаций, атлас 1024), Medieval Hexagon, Dungeon | GLTF/FBX |
| **Quaternius** (quaternius.com) | CC0 | Universal Base Characters + Universal Animation Library (есть glTF), Stylized Nature, Ultimate Animated Characters (FBX → конвертировать) | GLTF/FBX/Blend |
| **Poly Pizza** (poly.pizza) | CC0 / CC-BY (смотреть у каждой модели) | Точечные модели-декор | GLB |

- GFX-SRC-1: ОБЯЗАТЕЛЬНО вести `ASSETS_CREDITS.md`: пак, автор, URL, лицензия. CC-BY-ассеты — с атрибуцией на экране «Об игре».
- GFX-SRC-2: предпочитать ассеты одного стиля (low-poly, общий цветовой атлас) — это и единый визуал, и батчинг (один материал → мало draw calls).
- GFX-SRC-3: ассеты хранятся в репозитории в `public/assets/` уже оптимизированными (раздел 11.5). Исходники — в `assets-src/` (в `.gitignore`, если тяжёлые) либо скачиваются скриптом `scripts/fetch-assets`.

### 11.5 Конвейер ассетов (asset pipeline)

- GFX-PIPE-3: манифест `public/assets/manifest.json`: id, путь, треугольники, размер, лицензия, анимации. Генерируется скриптом, проверяется в CI на соблюдение бюджетов (PERF-BUDGET).
- GFX-PIPE-4: для превращения GLB в React-компоненты ОПЦИОНАЛЬНО `gltfjsx` (pmndrs).

## 12. Производительность (целевое железо: i3 4-5 gen, Intel HD, 6 ГБ ОЗУ)

### 12.1 Бюджеты (PERF-BUDGET) — проверяются автоматически
| Параметр | Бюджет |
|---|---|
| Треугольников в кадре (весь трек в кадре) | ≤ 80 000 |
| Треугольников на локацию | ≤ 15 000 |
| Треугольников на фигурку | ≤ 3 000 |
| Draw calls в кадре | ≤ 120 (статика локации — merged/instanced) |
| Текстуры | атласы ≤ 1024², суммарно в GPU ≤ 64 МБ |
| JS-бандл начальный (gzip) | ≤ 600 КБ; админка — отдельный lazy-чанк |
| Ассеты суммарно | ≤ 20 МБ; локации грузятся лениво (сначала видимая) |
| Память вкладки (Chrome Task Manager) | ≤ 400 МБ |
| Время до интерактива (холодный старт, 20 Мбит/с) | ≤ 8 с; повторный — ≤ 3 с (кэш) |
| FPS в активном режиме | 30 стабильно (cap 30) на Intel HD 4400 |
| FPS/CPU в фоне | 0 кадров, CPU вкладки ≈ 0% |

### 12.2 Режимы рендера (PERF-MODE)
- PERF-1: рендер по требованию (`frameloop="demand"`) + собственный тикер с ограничением **30 FPS** в активном режиме. Никаких бесконечных `requestAnimationFrame` без ограничителя.
- PERF-2: **Анимируется только то, что в кадре**: объекты локаций вне видимой области (frustum) не обновляются; локации «живые» только в активном окне.
- PERF-3: вкладка скрыта (`document.visibilityState === "hidden"`) → рендер-цикл остановлен полностью, опрос данных продолжается (раз в 60 с, лёгкий fetch).
- PERF-4: окно видимо, но не в фокусе (`blur`) → через 30 с (настраиваемо) заморозка: рендерится один статичный кадр, анимации стоп. При `focus` — возобновление.
- PERF-5: **Режим ТВ-табло** `?mode=tv`: игнорирует blur (офисный экран обычно не в фокусе), крутит анимации 30 FPS, автопрокрутка камеры по фигуркам, лидерборд по таймеру; скрыты кнопки админки.
- PERF-6: когда поверх карты открыт лидерборд/админка/модалка — сцена замораживается.
- PERF-7: бездействие пользователя > 2 мин (не ТВ-режим) → FPS снижается до 15, эмбиент продолжается.

### 12.3 Уровни качества (PERF-QUALITY)
| Уровень | DPR | Тени | Эффекты | Эмбиент |
|---|---|---|---|---|
| Low (дефолт для iGPU) | 0.75–1.0 | нет, «блоб»-тени (текстура под объектом) | нет | упрощённый (без частиц) |
| Medium | 1.0 | запечённые в текстуру/вершинные цвета | лёгкий fog | полный |
| High | min(devicePixelRatio, 1.5) | 1 направленный свет, shadow map 1024 только для фигурок | fog, лёгкий outline для фигурок | полный |

- PERF-8: автоопределение: стартуем в Low, замеряем FPS 5 с; если стабильно ≥ 55 при снятом cap — предлагаем Medium. Если FPS < 24 — снижаем DPR ступенями до 0.6, затем отключаем эмбиент, затем предлагаем 2D-режим. Выбор сохраняется в localStorage (в try/catch).
- PERF-9: запрещено по умолчанию: постпроцессинг (bloom, SSAO, DOF), физический движок, реалтайм-тени для статики, PBR с картами нормалей на всей сцене (используем `MeshLambertMaterial`/`MeshToonMaterial` или `MeshStandardMaterial` без лишних карт), прозрачность с сортировкой в больших количествах.
- PERF-10: антиалиасинг: `antialias: false` на Low, FXAA не использовать; на Medium/High — нативный MSAA если дешёво.
- PERF-11: `powerPreference: "low-power"` не использовать принудительно (на iGPU не влияет), `preserveDrawingBuffer: false`.
- PERF-12: ресурсы освобождаются при смене сезона/пака (`dispose` геометрий, материалов, текстур).

## 13. Архитектура

### 13.1 Ключевое решение: статический сайт + GitHub-репозиторий как хранилище
Бэкенд-сервера нет. Приложение — статический SPA на GitHub Pages. Общее состояние (конфиг сезона, данные импорта, корректировки) — JSON-файлы в том же репозитории. Админка пишет их коммитом через GitHub REST API (токен админа), GitHub Actions пересобирает и публикует сайт, клиенты опрашивают маленький `version.json`.

```
 [Excel у админа] --(парсинг в браузере, SheetJS)--> [Админка SPA]
                                                         |
                                     GitHub REST API (Git Data: blobs→tree→commit→ref)
                                                         v
                                   [Репозиторий: /data/*.json (зашифровано)]
                                                         |
                                     GitHub Actions: test → build → deploy
                                                         v
 [8–50 клиентов] <--- опрос data/version.json раз в 60 с --- [GitHub Pages (CDN)]
       \___ при смене rev: загрузка data/seasons/<id>/*.enc.json → расшифровка → движок → сцена
```

**Почему так (сравнение вариантов):**

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| **A. GitHub Pages + данные в репо** | 0 ₽, без карты, GitHub стабилен в сети; история версий = журнал + откат бесплатно; нет сервера | Задержка публикации ~1–2 мин; публичный репозиторий (решается шифрованием, 13.6) | **Выбрано** |
| B. GitHub Pages + Firebase Firestore (Spark) | Realtime, приватные правила доступа, без задержки | Второй аккаунт/проект Google Cloud, квоты, больше кода авторизации | Запасной вариант: реализуется за интерфейсом `StorageAdapter` |
| C. Google Apps Script + Google Sheets как БД | Бесплатно, привычные таблицы | Медленные ответы, лимиты одновременных выполнений, сложно тестировать | Не выбран |
| D. Свой сервер/VPS | Полный контроль | Не бесплатно, нужна поддержка | Не выбран |

- ARCH-1: весь доступ к данным — через интерфейс `StorageAdapter { load(): Promise<Snapshot>; getVersion(): Promise<Version>; commit(changes, baseRev, message): Promise<Version> }`. Реализации: `GitHubPagesAdapter` (дефолт), `LocalFileAdapter` (dev/тесты), ОПЦИОНАЛЬНО `FirestoreAdapter`.
- ARCH-2: клиент хранит в state **входные данные** (конфиг, записи, корректировки), а производное (баллы, позиции, ачивки) вычисляет движок на клиенте. Объём мал (NFR-LOAD-3), расчёт < 50 мс.
- ARCH-3: движок — `src/engine/`, без зависимостей от React/three/браузера. Вход: `(config, records, adjustments, imports, now)`. Выход: `GameState`.

| Слой | Технология | Примечание |

**Почему не другой движок:**
- Godot (веб-экспорт): тяжёлый wasm-рантайм (десятки МБ), многопоточный экспорт требует заголовков COOP/COEP, которые GitHub Pages не задаёт; дольше старт на слабом ПК.
- Babylon.js: мощнее, но тяжелее бандл; преимуществ для нашей сцены нет.
- Phaser / PixiJS: 2D; «вид под 45°» пришлось бы делать пререндеренными спрайтами — меньше гибкости при смене фигурок/локаций.
- three.js + R3F: лёгкий, glTF «родной», крупнейшая экосистема и готовые скиллы для Claude Code, UI и 3D в одной модели (React).

### 13.3 Решение по open-source основе
- Проверены: клоны «Монополии» (2D, круговое поле, логика ходов игроков — нам не подходит), `coldi/r3f-game-demo` (MIT, тайловая игра на R3F — автор прямо рекомендует использовать как вдохновение, а не основу, и не поддерживает код).
- **Решение:** не форкать чужую игру, а собрать из готовых блоков: шаблон `vite react-ts` + экосистема pmndrs (R3F/drei/zustand) + CC0-ассеты + готовые скиллы. Из `r3f-game-demo` можно заимствовать паттерны тайлового перемещения.

### 13.5 Запись данных и доступ админа
- SEC-1: админ создаёт **fine-grained personal access token** GitHub: доступ только к одному репозиторию, права `Contents: Read and write` (+ `Metadata: Read`), срок 90–365 дней.
- SEC-2: токен вводится в админке, хранится в `localStorage` этого браузера (в try/catch), никогда не коммитится и не логируется. Кнопка «Выйти» удаляет токен.
- SEC-3: по заголовку ответа GitHub `github-authentication-token-expiration` админка предупреждает о скором истечении токена (за 14 дней).
- SEC-4: запись — атомарный коммит нескольких файлов через Git Data API (blobs → tree → commit → update ref без `force`). Если ref ушёл вперёд (другой админ) — 409/422 → перечитать, пересчитать, повторить (ADM-2).
- SEC-5: сообщение коммита: `data(<seasonId>): <тип действия> — <кратко> [by <github login>]`. История коммитов = аудит-журнал и основа для ADM-UNDO.

### 13.6 Конфиденциальность данных (ВАЖНО)
Бесплатный GitHub Pages публикует сайт из **публичного** репозитория (приватный репозиторий с Pages — платный тариф). В данных — ФИО и показатели продаж. Поэтому:
- SEC-6: все файлы с ПДн и показателями хранятся **зашифрованными** (`*.enc.json` = `{v, alg:"AES-GCM", salt, iv, ciphertext}`), ключ = PBKDF2(SHA-256, ≥100 000 итераций) от общей парольной фразы.
- SEC-7: парольная фраза передаётся сотрудникам в ссылке после `#` (`https://<user>.github.io/<repo>/#/?k=<фраза>`) — фрагмент URL не отправляется на сервер. После первого открытия фраза сохраняется в localStorage и убирается из адресной строки. Без фразы — экран «Введите код доступа».
- SEC-8: смена фразы — в админке (перешифровка всех файлов одним коммитом). Старые коммиты в истории остаются зашифрованы старой фразой — при утечке ссылки считать историю скомпрометированной; при необходимости — пересоздание репозитория.
- SEC-9: это защита от случайного доступа из интернета, а не от сотрудников со ссылкой. Раздел «Об игре» честно это описывает.
- SEC-10: в репозиторий никогда не попадают исходные Excel-файлы, телефоны, суммы сделок, данные клиентов.

### 13.7 Синхронизация клиентов
- SYNC-1: клиент раз в 60 с (настраиваемо, 30–300 с) запрашивает `data/version.json?t=<timestamp>` с `cache: "no-store"` (обход CDN-кэша Pages). Если `rev` изменился — загружает изменённые файлы сезона.
- SYNC-2: кнопка «Обновить» (FR-LB-4) — немедленная проверка.
- SYNC-3: при ошибке сети — показывать последнее состояние из кэша (localStorage/IndexedDB в try/catch) с плашкой «нет связи, данные от ЧЧ:ММ»; ретраи с экспоненциальной задержкой.
- SYNC-4: админ после коммита видит новое состояние сразу (локально), а баннер «публикуется… ~1–2 мин» гаснет, когда `version.json` на Pages отдаёт новый `rev`.

## 15. Деплой

- DEP-1: хостинг — **GitHub Pages**, публикация через GitHub Actions (`actions/upload-pages-artifact` + `actions/deploy-pages`). Репозиторий публичный (13.6).
- DEP-2: workflow `deploy.yml`: триггер `push` в `main`; шаги: `npm ci` → `npm run typecheck` → `npm test` (движок, пропускается, если изменились только `data/**`) → `npm run build` → копирование `data/` в `dist/data/` → деплой. `concurrency: { group: "pages", cancel-in-progress: false }`.
- DEP-3: SPA-роутинг — `HashRouter` (у Pages нет фолбэка на index.html для глубоких ссылок).
- DEP-4: Vite: хэшированные имена ассетов (долгий кэш браузера), `data/*` запрашивается с cache-busting (SYNC-1).
- DEP-5: ожидаемая задержка «импорт админа → видно всем» ≈ 1–2 мин (время Actions). Для этой игры приемлемо; если станет критично — переход на вариант B (Firestore) через `StorageAdapter`.
- DEP-6: лимиты Pages (размер сайта ~1 ГБ, мягкий лимит трафика ~100 ГБ/мес) с запасом покрывают бюджет ассетов 20 МБ × 50 устройств (плюс кэш браузера).
- DEP-7: запасные бесплатные хостинги для того же статического билда: Cloudflare Pages, Netlify (проверить доступность из корпоративной сети перед переездом).
- DEP-8: README: пошаговая инструкция для не-разработчика — создать репозиторий, включить Pages (Source: GitHub Actions), создать токен, задать фразу доступа, открыть админку, загрузить шаблон сезона.

## 19. Допущения, риски, открытые вопросы

### 19.1 Допущения
- A-1: Браузер на рабочих ПК — Chromium-based актуальной версии с WebGL2.
- A-2: `*.github.io` и `api.github.com` доступны из корпоративной сети (подтверждено: GitHub работает стабильно).
- A-3: Данные обновляет только админ импортом Excel; «реального времени» не требуется, задержка публикации 1–2 мин приемлема.
- A-4: Менеджеры видят показатели друг друга в лидерборде (так задумано игрой).
- A-5: Руководители групп — фигурки, но не участники лидерборда менеджеров (если у них есть личные продажи — `[ОТКРЫТЫЙ ВОПРОС]`).

### 19.2 Риски
| ID | Риск | Мера |
|---|---|---|
| R-1 | Публичный репозиторий с ФИО и показателями | Шифрование (13.6); исходники Excel не коммитятся |
| R-2 | Утечка токена админа | Fine-grained токен на 1 репозиторий, срок, кнопка выхода, хук против коммита токена |
| R-3 | Пороги ачивок/цели не откалиброваны → ачивки у всех или ни у кого | Первый месяц — «калибровочный»; в админке статистика «сколько человек получило каждую ачивку» |
| R-4 | Слабый iGPU / драйвер в чёрном списке WebGL | Уровни качества, автоснижение, 2D-фолбэк (GFX-6) |
| R-5 | Изменится формат рабочих таблиц | Профили импорта (9.2), мастер сопоставления |
| R-6 | Смена весов посреди месяца «откатывает» фигурки | Превью ADM-PREVIEW, журнал, отмена |
| R-7 | GitHub Pages станет недоступен | Тот же билд переносится на Cloudflare Pages/Netlify; данные — через `StorageAdapter` |
| R-8 | Мотивационный перекос: гонка за счетами 6+ в ущерб оплатам | Веса (оплата ×10), ачивка «Конвертер», контроль динамики в первый месяц |

### 19.3 Открытые вопросы (вынести в `docs/OPEN_QUESTIONS.md`)
1. Формат рабочих таблиц: построчно по дням, накопительный итог или сырые события? Какие колонки? (реализовано через профили; нужен пример файла)
2. Счёт с разговором 20+ входит ли в число счетов 6+ в исходной таблице? (FR-SCORE-3)
3. Есть ли план в баллах/штуках на команду или менеджера? Если нет — утвердить `targetPointsPerManager`.
4. Правило разбиения месяца на 4 недели (FR-TRACK-5).
5. Нужна ли блокировка прохода локации до начала недели (`gateByWeek`)?
6. Участвуют ли руководители групп в лидерборде своими продажами?
7. Сколько админов и кто?
8. Предпочтения по тематике 4 локаций (дефолт: деревня → город → горы/замок → порт).
9. Можно ли показывать фото руководителей на фигурках?
