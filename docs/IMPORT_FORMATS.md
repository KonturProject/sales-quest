# Форматы выгрузок для импорта

Разобраны 27.09.2026 по двум реальным выгрузкам за сентябрь 2026. Сами файлы лежат только
локально у автора и в git не попадают (`*.xlsx` в `.gitignore`, SEC-10). В этом документе —
только структура и правила, без ФИО, клиентов и сумм.

Разметку полей подтвердил автор требований 27.09.2026 (см. D-22 в [`DECISIONS.md`](DECISIONS.md)).

## Итог: какая метрика откуда

| Метрика (id) | Название в игре | Файл | Поле | День, к которому относим |
|---|---|---|---|---|
| `inv6` | Качественные счета | Воронка по дням, лист «ВОРОНКА Первичная кампания» | блок «Качественные счета» → подблок «Качественные счета, шт.» | дата колонки |
| `inv20` | Разговоры от 20 минут | Воронка по дням, тот же лист | блок «Разговоры от 20 минут» → подблок «Разговоры от 20 минут, шт.» | дата колонки |
| `pay` | Оплаты | Детальные данные по оплаченным счетам | одна оплата = один уникальный «№ счета» (без «Академии») | «Дата оплаты» |

Id метрик оставлены как в ТЗ (`inv6`, `inv20`, `pay`) — на них ссылаются формулы и ачивки;
меняются только названия в конфиге сезона. `inv6` — счета, `inv20` — разговоры, это разные
сущности, поэтому `metricsCounting = "exclusive"`: каждая метрика берётся как есть.

## 1. Воронка по дням (форма «матрица», D-19)

Выгрузка вида `…_Воронка_Дни_<фамилия>.xlsx`, около 16 МБ.

### Листы

| Лист | Берём? | Что в нём |
|---|---|---|
| «ВОРОНКА Первичная кампания» | **да** | сводная по сотрудникам и дням, 20 блоков показателей |
| «ВОРОНКА ПНС» | нет | только трафик и время разговоров |
| «Лист1» (скрытый) | нет | пустой |

Лист «ВОРОНКА ПНС» объявляет диапазон до строки 1 048 576. Парсер читает **только нужный лист**
(SheetJS `read(…, { sheets: [...] })`) — лишний лист даёт только лишнее время и память.
Импорт выполняется в админке на ПК координатора (i5 12-го поколения), строгие бюджеты
производительности к нему не применяются (D-7a).

### Шапка (строки 1–8)

| Строка | Что в ней |
|---|---|
| 1–3 | пустые |
| 4 | G — месяц («Сентябрь.2026»); с колонки H — **названия блоков**. Блок начинается в колонке, где в строке 4 есть текст, и идёт до начала следующего блока |
| 5 | B — «группа», C — «сотр» (заголовки колонок-флагов); в блоках — **названия подблоков** («…, шт.», «Доля …», «План» / «Факт» / «Выполнение») |
| 6 | **даты**: рабочие дни пн–пт (Excel-даты) и после каждой пятницы — колонка итога недели с текстом `ГГГГ.НН` (ISO-неделя) |
| 7 | «Общий итог» по отделу — пропускаем |
| 8 | «Названия строк» — пропускаем |

Каждый подблок — 30 колонок: 5 недель × (5 дней + итог недели). Колонки итога недели
(строка 6 — текст, а не дата) пропускаем.

### Строки данных (с 9-й)

| Колонка | Смысл |
|---|---|
| B = 1 | строка **группы** (итог по группе); G — название группы |
| C = 1 | строка **сотрудника**; G — ФИО; сотрудник относится к ближайшей группе выше |
| A, B, C = 0 и пустая G | хвост сводной — пропускаем |

Значения — целые числа; пустая строка `''` — нет данных, считаем 0. Блоки со временем
(длительности) не используем.

### Нужные блоки

Блоки ищем **по названиям в строках 4 и 5, а не по буквам колонок**: буквы сдвинутся,
если в сводную добавят блок.

| Метрика | Строка 4 (блок) | Строка 5 (подблок) | Колонки в примере |
|---|---|---|---|
| `inv6` | «Качественные счета» | «Качественные счета, шт.» | AEL…AFO |
| `inv20` | «Разговоры от 20 минут» | «Разговоры от 20 минут, шт.» | LZ…NC |

Остальные блоки в игру не идут: средний трафик, взятые и завершённые (с планом), разговоры
до 1 минуты и от 6 минут, среднее время разговора и первичного звонка, презентации 1–3 и от 20 мин,
счета, клиенты с отправленными заказами, некачественные счета, презентации с заказами,
действия без звонка, конверсия из звонка в оплату. План в воронке есть только по звонкам,
по счетам и оплатам — нет; нормативы операторов задаются в админке (ADM-ROSTER-2).

### Период

Воронка покрывает полные ISO-недели, задевающие месяц (в примере — 31.08…02.10). Даты вне
периода сезона отбрасываются с предупреждением (DATA-7).

### Группы

В примере 6 групп — это 6 команд. Названия вида `<площадка>_НП_СР_<город>_СР<n>_<направление>`;
код команды — `СР<n>` (регулярное выражение `СР\d+`; первое «СР» без цифры не совпадает).
Численность групп — от 5 до 16 человек (ТЗ предполагало 4–12; движок размер не ограничивает).

## 2. Детальные данные по оплаченным счетам (форма «события»)

Выгрузка вида `Детальные данные по оплаченным счетам_*.xlsx`, один лист. Строка 1 — заголовки,
дальше одна строка = одна позиция оплаченного счёта. Последняя строка «Сумма заказа»
(объединённые A:B, итоги) и пустые строки после неё — пропускаем.

| Колонка | Тип | Берём | Зачем |
|---|---|---|---|
| Пин | текст | нет | id клиента |
| № счета | текст | только при импорте | один № = одна оплата; в хранилище не пишется |
| Дата оплаты | дата | **да** | день, к которому относим оплату |
| Группа | текст | только при импорте | код команды `СР<n>` — подсказка и проверка команды оператора (DATA-11) |
| Автор | текст | **да** | ФИО оператора → сопоставление (DATA-9) |
| Клиент | текст | **нет** | данные клиента (SEC-10) |
| ИНН | текст | **нет** | данные клиента (SEC-10) |
| Издание, Головной продукт, Предложение | текст | нет | |
| Тип головного продукта | текст | фильтр | «Академия» не считаем |
| Дата продажи | дата | нет | бывает пустой; может отличаться от даты оплаты |
| К-во | число | нет | в примере всегда 1 |
| Подписка с, Подписка по | дата | нет | |
| Сумма | число | **нет** | суммы сделок (SEC-10) |
| Статус новизны | текст | нет | считаем все статусы: «Новая», «Расширение», «Реактивация» |
| Блокировка содержимого, Период последней предыдущей подписки, Категория подписки, Состояние активной подписки | — | нет | |

### Правила подсчёта `pay`

1. Строки без «Дата оплаты» или без «Автор» пропускаем (итоговая строка).
2. «Тип головного продукта» = «Академия» — не считаем (обучение за символическую сумму — подарок к продаже).
3. Один «№ счета» = одна оплата: несколько строк одного счёта (позиции) схлопываются. Дата и автор —
   из первой строки; если у строк одного счёта разные автор или дата — предупреждение в отчёте импорта.
4. `pay(оператор, день)` = число уникальных счетов с этой датой оплаты.

## 3. Как два файла складываются в данные игры

- **Каждая выгрузка заменяет только свои метрики** (D-20): воронка — `inv6` и `inv20`,
  оплаченные счета — `pay`. Ключ записи — (оператор, дата, метрика). Повторная загрузка того же
  файла ничего не меняет (DATA-5).
- **Файл считается полным за свой период.** Воронка — по датам своих колонок. Счета — от первой до
  последней даты оплаты в файле (админ может поправить период в мастере импорта). У операторов
  групп, которые есть в файле, дни периода без оплат получают `pay = 0` — так отменённая или
  перенесённая оплата исчезает после повторной выгрузки (OQ-12).
- **В хранилище (зашифровано) попадают только агрегаты** «оператор × день × метрика».
  Номера счетов, клиенты, ИНН, суммы, продукты — нет.

## 4. Сопоставление операторов и команд

- ФИО в обоих файлах полные («Фамилия Имя Отчество») и совпадают между файлами. Встречается «ё» —
  нормализация по DATA-9 (`ё → е`, пробелы, регистр).
- Команда в конфиге сезона получает поле `sourceCode` — код группы в выгрузках (`СР1`, …, D-21).
  По нему импорт подсказывает команду нового оператора и предупреждает, если оператор в выгрузке
  числится в другой группе, чем в составе (возможно, перевод).
- Первая настройка сезона: состав можно создать из воронки (все сотрудники по группам),
  затем админ задаёт руководителей и нормативы — предложение для этапа 2.

## 5. Проверить на этапе 2

- Разбор 16-МБ воронки в браузере (только нужный лист) проходит без ошибок и за разумное время
  на ПК координатора; код разбора живёт только в lazy-чанке админки (D-7a).
- Тестовые фикстуры (QA-2) — синтетические xlsx той же структуры с вымышленными ФИО,
  генерируются скриптом; реальные выгрузки в репозиторий не попадают.
- Стабильность формата воронки от месяца к месяцу — сверить по выгрузке следующего месяца (OQ-13).
